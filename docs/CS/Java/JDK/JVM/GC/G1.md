## Introduction

Garbage-First（G1）[垃圾回收器（GC）](/docs/CS/Java/JDK/JVM/GC/GC.md?id=collectors) 自 JDK 9 起成为默认 GC。<br/>

> [!NOTE]
> JDK 9 起 G1 只对 **server 环境**默认，受限环境（单 CPU，或物理内存 < 1792 MB）会回落 Serial；**JDK 27 起 G1 成为所有环境的默认 GC**（[JEP 523](https://openjdk.org/jeps/523)）。下文「面向多处理器、大内存的 server 风格收集器」是对其**设计取向**的描述，不代表它仍是可选收集器。
Garbage-First（G1）是一种 server 风格的垃圾回收器，**面向多处理器、大内存机器**设计。
它试图以较高概率满足垃圾回收（GC）停顿时间目标，同时保持高吞吐量。<br/>
全局标记等全堆操作与应用线程并发执行，从而避免了与堆大小或存活数据量成比例的中断。

G1 的首要目标是为运行需要大堆、对 GC 延迟有明确限制的应用的用户提供解决方案。
**这意味着堆大小约 6 GB 或更大，且停顿时间稳定可预测，低于 0.5 秒。**

目前使用 CMS 或 Parallel Compaction 的应用，如果具有以下一个或多个特征，切换到 G1 会受益。

- Java 堆中超过 50% 被存活对象占用。
- 对象分配率或晋升率波动显著。
- 应用正在经历不期望的长时间垃圾回收或压缩停顿（超过 0.5 至 1 秒）。

G1 在应用运行的同时完成部分工作，它牺牲了原本可供应用使用的处理器资源，以换取更短的回收停顿。

这一点在应用运行时有一个或多个垃圾回收线程活跃最为明显。
因此，与吞吐量优先的收集器相比，G1 收集器的垃圾回收停顿通常更短，但应用吞吐量也往往略低。

G1 是一种分代式、增量式、并行、大部分并发、Stop-The-World（STW）、基于疏散的垃圾回收器，在每次 STW 停顿中监控停顿时间目标。
与其他收集器类似，G1 将堆划分为（虚拟的）年轻代和老年代。
空间回收工作集中在年轻代，因为那里的回收效率最高，老年代则偶尔进行空间回收。

部分操作始终在 STW 停顿中执行以提高吞吐量。
其他操作如全局标记等全堆操作，如果在应用停止时执行会耗时较长，因此改为与应用并行和并发执行。
为了保持空间回收的 STW 停顿简短，G1 将空间回收分成多个步骤增量执行，并采用并行方式。
G1 通过追踪先前应用行为和垃圾回收停顿的信息来建立相关成本模型，以此实现可预测性。
它利用这些信息来控制停顿中需要完成的工作量。例如，G1 首先在回收效率最高的区域回收空间（即那些大部分被垃圾填满的区域，这也是其名字的由来）。

G1 主要通过疏散来回收空间：选中的要回收的内存区域中的存活对象被复制到新的内存区域，过程中完成压缩。
疏散完成后，之前被存活对象占用的空间可以重新供应用分配使用。

Garbage-First 收集器不是实时收集器。
它试图在较长时间内以较高概率满足设定的停顿时间目标，但无法对每一次停顿都做到绝对保证。

## JDK 22–27 Evolution

> [!NOTE]
> 本篇版本基线为 **JDK 27**。下表汇总 JDK 22 以来影响 G1 行为与实现的关键 JEP / bug fix，后续各节会在对应处内联更新并交叉引用。

| JEP / Bug | Release | 领域 | 变化摘要 |
| :-- | :-- | :-- | :-- |
| [JEP 423](https://openjdk.org/jeps/423) | 22 | GC 暂停 | **Region Pinning**：JNI critical 区域不再禁用 GC，改为 pin 住含 critical object 的 region（见 [Region Pinning](#region-pinning-jep-423)） |
| [JEP 475](https://openjdk.org/jeps/475) | 24 | C2 编译 | **Late Barrier Expansion**：G1 写屏障从 C2 编译管道早期移到后期（寄存器分配后），减少 JIT 编译开销（见 [Late Barrier Expansion](#late-barrier-expansion-jep-475)） |
| [JDK-8343782](https://bugs.openjdk.org/browse/JDK-8343782) | 25 | RSet | **Shared G1CardSet**：预期一起回收的 old gen regions 分组后共享一个 G1CardSet 实例，消除组内跨 region 引用追踪（见 [Remembered Set](#remembered-set)） |
| [JEP 522](https://openjdk.org/jeps/522) | 26 | 写屏障 | **Dual Card Table**：双卡表原子交换，消除 mutator 与 refinement 线程间的同步，写屏障从 ~50 指令降到 ~12，吞吐量提升 5–15%（见 [Dual Card Table](#dual-card-table-jep-522)） |
| [JDK-8048180](https://bugs.openjdk.org/browse/JDK-8048180) | 26 | Humongous | **Eager Reclamation of Humongous Objects with References**：含引用的大对象也能在任意 GC pause 中被回收（不再仅限基本类型数组，见 [Humongous Objects](#humongous-objects)） |
| [JEP 523](https://openjdk.org/jeps/523) | 27 | 默认值 | **G1 成为所有环境默认 GC**，废止受限环境（单 CPU / 堆 < 1792 MB）回落 Serial 的规则（见本篇引言） |
| [JDK-8238686](https://bugs.openjdk.org/browse/JDK-8238686) | 27 | 堆伸缩 | **MinHeapFreeRatio / MaxHeapFreeRatio 默认值从 40/70 改为 0/100**，默认不再影响 G1 堆伸缩（见 [Heap Sizing](#heap-sizing)） |

> [!TIP]
> JDK 26 的 JEP 522（双卡表）与 JDK 27 的 JEP 523（G1 全环境默认）构成了 G1 的"收官之战"：吞吐量已接近 Parallel GC，延迟本就优于 Serial / Parallel，现在连最小堆场景也默认选中它。G1 不再需要与 Parallel 做"吞吐 vs 延迟"的二选一——它已经是通用场景的最优解。

## Knowledge Map

G1 已拆分为 8 篇独立笔记，下表给出每篇的覆盖范围。阅读顺序建议：**Architecture → Predictions → Barrier → RSet → ConcurrentMarking → Evacuation → MixedGC → FullGC**。

### Architecture

**Heap 分区模型、GC 周期、停顿与 CSet 选择。**

- Heap region 五种类型编码（Free / Eden / Survivor / Old / Humongous / Archive）
- Region Lifecycle State Machine：Free → Eden → Survivor → Old → Free 的状态转换
- HeapRegionManager：两层索引表、三个并行 free list、linear-scan claimed-bit 迭代器、Retirement 机制
- Heap sizing：MinHeapFreeRatio / MaxHeapFreeRatio、堆自适应 resize 策略
- Humongous 对象：分配路径、starts / continues 编码、eager reclamation

### Pause-Time Prediction

**G1Predictions 自适应停顿模型、IHOP 自适应、Young Gen / CSet 尺寸决策。**

- G1Predictions 架构：TruncatedSeq × 5 指标、EWMA、truncated_mean 抗异常值
- 三条决策闭环：Young Gen 尺寸（`G1NewSizePercent` 5% / `G1MaxNewSizePercent` 60%）、Mixed GC CSet 选择（`-XX:G1MixedGCCountTarget` 默认 8）、IHOP 自适应（`G1AdaptiveIHOPControl` 公式）
- MMU 约束：`-XX:GCPauseIntervalMillis`（默认 200ms）节流机制

### Barrier

**写屏障、Region Pinning（JEP 423）、Late Barrier Expansion（JEP 475）、Card Marking 基础。**

- JEP 423：JNI critical region pinning、`_critical_objects_count` 计数器、`is_pinned()` 检查、evacuation failure 升级为 promotion
- JEP 475：barrier 从 C2 IR 阶段延后到 register allocation 之后的 code generation 阶段
- 传统 card marking + G1 relaxed invariant（`l` 偏移容差）
- JEP 522 双卡表改动（dual card table）跨章节引用

### RSet

**Remembered Set 维护全流程：Refinement 线程、RSet 三级粒度、G1CollectedHeap 与 Root Scanning 内部结构。**

- RSet 三级粒度：Coarse → Medium → Fine 的渐进式精确与成本权衡
- ConcurrentRefineThread 调度：primary + secondary workers、DCQS 消费主循环
- JEP 522 对 refinement 的影响：dual table 下直接标脏 primary table
- G1CollectedHeap 类结构、HeapRegionManager 入口
- Root Scanning：`G1RootProcessor::process_java_roots`（CLDG + Threads 并行）+ `process_vm_roots`

### ConcurrentMarking

**SATB 并发标记全机制：三色标记、TAMS、Finger 算法、do_marking_step 核心循环、与 Evacuation 并发交互。**

- SATB（Snapshot-At-The-Beginning）正确性原理：初始快照 + 写屏障记录旧值
- TAMS（Top At Mark Start）：隐式标记 + 零成本新分配对象标记
- Finger 算法：bitmap（above-finger gray）+ mark stack（below-finger gray）双灰度表示
- `G1CMTask::do_marking_step` 核心循环：SATB drain → mark stack DFS → finger bitmap 扫描 → 时间片中断
- 并发标记 7 阶段完整周期 + `wait_for_root_region_scanning()` correctness 硬约束
- Evacuation 与 Marking 的并发交互：mark stack 作为额外 GC Root、TAMS 在 evacuation 后更新

👉 [**跳转 → G1/ConcurrentMarking.md**](/docs/CS/Java/JDK/JVM/GC/G1/ConcurrentMarking.md)

### Evacuation

**Young GC 的 Cheney 复制全流程：四步闭环、PLAB 分配、mark-word forwarding、age promotion、evacuation failure。**

- 完整调用链：`G1ParTask::work` → `trim_queue_to_threshold` → `do_oop_work` → `copy_to_survivor_space`
- 步骤 1：CSet 判定 + mark-word forwarding 状态检查（lock bits `01→11` 编码）
- 步骤 2：PLAB 三层分配（PLAB bump-pointer → 新 PLAB 申请 → region CAS 竞争）+ Age Promotion（`MaxTenuringThreshold` 默认 15 + survivor 容量动态阈值）
- 步骤 3 & 4：引用更新 + RSet 维护（跨 region 引用判定 + JEP 522 交叉引用）
- 大数组特殊处理：`ParGCArrayScanChunk`（默认 50）→ `_partial_array_queue`
- Evacuation Failure：就地晋升到 old gen + Full GC 升级

👉 [**跳转 → G1/Evacuation.md**](/docs/CS/Java/JDK/JVM/GC/G1/Evacuation.md)

### MixedGC

**Mixed GC 触发条件、CSet 候选选择、分段 evacuate、IHOP 自适应循环、ConcurrentMarkThread 生命周期。**

- 触发时机两条件：并发标记完成 + `G1HeapWastePercent`（默认 5）可回收空间
- CSet 候选选择算法：Cleanup 阶段 `G1MixedGCLiveThresholdPercent`（默认 85）筛选 + 存活字节数升序排序
- 每次 Mixed GC 从候选池按停顿预算分段消费（`G1OldCSetRegionThresholdPercent` 默认 10% region 上限）
- Mixed GC evacuation 与 Young GC 的三个差异 + `should_mark` 参数交互
- `need_to_start_conc_mark`：每次分配请求时的 IHOP 判定入口
- `G1ConcurrentMarkThread` 生命周期 + `concurrent_mark_cycle_do` 源码参考
- GCCause 分发：`VM_G1CollectForAllocation` vs `VM_G1CollectFull` vs `try_collect_concurrently`

👉 [**跳转 → G1/MixedGC.md**](/docs/CS/Java/JDK/JVM/GC/G1/MixedGC.md)

### FullGC

**Full GC 四阶段并行压缩算法 + Tuning 参数 + Development 与 Pros/Cons。**

- Evacuation vs Full GC 对比表（压缩粒度、引用更新时机、并发度）
- Phase 1 STW 并行标记：纯 STW 三色标记 + 弱引用处理 + 类卸载
- Phase 2 Prepare Compaction：Compaction Point 核心设计、forwarding pointers 计算、串行压缩兜底
- Phase 3 Adjust Pointers：preserved marks → weak roots → GC roots → region by region 的依赖顺序
- Phase 4 Do Compaction：按 Phase 2 规划好的顺序搬运对象
- Tuning 参数集：MaxGCPauseMillis、G1MixedGCLiveThresholdPercent、InitiatingHeapOccupancyPercent 等
- Development 演进 + Pros/Cons 适用场景
