## Introduction

C2（`CompLevel_full_optimization`，值为 4，`compiler/compilerDefinitions.hpp:61`）是 HotSpot 的 **server 层优化编译器**：吃进去的是字节码 + 解释器/C1 采集到的 profile 数据（MDO），吐出来的是安装进 [CodeCache](/docs/CS/Java/JDK/JVM/CodeCache.md) 的 `nmethod`。它与 C1 的分工不在功能而在优化深度：

| 维度 | C1（[c1](/docs/CS/Java/JDK/JVM/c1.md)） | C2（本篇） |
| :-- | :-- | :-- |
| 编译层级 | `CompLevel_simple`(1) / `limited_profile`(2) / `full_profile`(3) | `CompLevel_full_optimization`(4) |
| 中间表示 | HIR → LIR → 机器码（三段式，无全局优化框架） | Ideal 图（机器无关）→ Mach 图（机器相关） |
| 优化手段 | 基本块内的简单优化、延迟填充、线性扫描分配寄存器 | GVN、逃逸分析、内联、循环变换、CCP、SuperWord、图着色寄存器分配 |
| 编译速度 | 快（毫秒级） | 慢（几十到上百毫秒，与图大小成正比） |
| 产出代码质量 | 接近解释器的数倍 | 峰值性能的主要来源 |

一次 C2 编译的完整生命周期是一条单线程管线（运行在 [CompilerThread](/docs/CS/Java/JDK/JVM/Thread.md?id=compilerthread) 上，由 CompileBroker 驱动）：

```text
C2Compiler::compile_method         入口：解析降级开关，失败可带开关重试
  └─ Compile::Compile              构造：建 node arena / alias 表 / 内联树根，随后
       ├─ Init                     初始化 env 记录器与全局结构
       ├─ Parse                    字节码 → Ideal 图（TracePhase _t_parser）
       ├─ Optimize                 机器无关优化（_t_optimizer）
       ├─ Code_Gen                 指令选择 → 调度 → 寄存器分配 → 输出 → 安装
       └─ ~Compile                  arena 整体回收，编译期结构一次性消失
```

后续章节按这条管线展开：先看入口的**降级阶梯**，再依次拆 Ideal 图、Parse（含 OSR 变体）、Profile 驱动的优化决策、GVN、Optimize 的各阶段，最后是 Code_Gen 的后端四段（匹配、调度、寄存器分配、输出安装）与调试信息。

## Version Baseline

> [!NOTE]
> **版本口径**：本篇源码摘录与 `文件:行号` 全部来自 **jdk-27-ga**（commit `815ff4d`，2026-09-15 GA，非 LTS；LTS 基线 JDK 25，下个 LTS 是 JDK 29）。子树的整体版本基线见 [JVM 版本基线](/docs/CS/Java/JDK/JVM/JVM.md?id=version-baseline)。

C2 的宏观架构（Ideal 图 + GVN + Chaitin-Briggs 寄存器分配）自 JDK 6 引入后一直稳定，但**细节层面的变化足以让旧文章失效**：本篇不集中罗列差异，而是在正文对应处以 WARNING / NOTE 就地标注。三处最值得注意的：

1. **`retry_class_loading_during_parsing` 已被移除**：jdk-27 的 `C2Compiler::compile_method` 只剩 6 个 `retry_no_*` 降级开关，基于 JDK 8/11 的老文章列的七级阶梯（含 class loading 重试）在 27 上不存在。

## Entry And Degradation Ladder

编译线程取到任务后调 `C2Compiler::compile_method`（`c2compiler.cpp:123`，调用点 `compiler/compileBroker.cpp:2041`；`-XX:+RepeatCompilation` 时还会以 `install_code=false` 再编一次，`compileBroker.cpp:2053`）。它的核心是一个**带降级开关的重试循环**：先把 7 个优化开关的初值读出来，失败时按固定顺序关掉其中一个再重编，保证每轮「必须取得进展」（每个分支都有 `assert(..., "must make progress")`）。

```cpp
// c2compiler.cpp:128-134
  bool subsume_loads = SubsumeLoads;
  bool do_escape_analysis = DoEscapeAnalysis;
  bool do_iterative_escape_analysis = DoEscapeAnalysis;
  bool do_reduce_allocation_merges = ReduceAllocationMerges && EliminateAllocations;
  bool eliminate_boxing = EliminateAutoBox;
  bool do_locks_coarsening = EliminateLocks;
  bool do_superword = UseSuperWord;
```

这些开关被装进 `Options` 结构（`compile.hpp:177-219`，共 8 个字段，最后一个是 `_install_code`），随 `Compile` 构造函数传入，编译期各处通过 `C->do_escape_analysis()` 之类访问器读取——**一次编译的优化策略在入口就定死了，中途不再改变**。

| 顺序 | 失败原因（`c2compiler.cpp` 行号） | 关掉的开关 | 重试方式 |
| :-- | :-- | :-- | :-- |
| 1 | `retry_no_subsuming_loads()`（151） | `subsume_loads`（153） | `report_failure` + `continue` |
| 2 | `retry_no_escape_analysis()`（157） | `do_escape_analysis`（159） | 同上 |
| 3 | `retry_no_iterative_escape_analysis()`（163） | `do_iterative_escape_analysis`（165） | 同上 |
| 4 | `retry_no_reduce_allocation_merges()`（169） | `do_reduce_allocation_merges`（171） | 同上 |
| 5 | `retry_no_locks_coarsening()`（175） | `do_locks_coarsening`（177） | 同上 |
| 6 | `retry_no_superword()`（181） | `do_superword`（183） | 同上 |

> **与旧认知的差异**：`retry_class_loading_during_parsing` 在 jdk-27-ga 已不存在（全树 grep 零匹配），旧文的七级阶梯（含 class loading 重试）对 27 失效；`DoIterativeEscapeAnalysis` 也不是 flag（见 `c2compiler.cpp:130`，直接抄 `DoEscapeAnalysis`）。

## The Compile Object

`Compile` 对象（`compile.cpp:636-905`）承载**一次编译的全部状态**，方法编译与 runtime stub 编译各有一个构造重载（stub 版 `compile.cpp:916-1037`，`_compile_id` 为 0、用 `Options::for_runtime_stub()`，编完直接进 `Code_Gen`）。构造函数里值得记住的成员：

- **双 node arena**（`compile.cpp:684-686`）：`_node_arena_one` / `_node_arena_two`，`_node_arena` 初始指向 one，matcher 阶段会交换新旧空间；
- `_compile_id`（639，取自 `ci_env->compile_id()`）、`_entry_bci`（642，OSR 编译时即 `osr_bci`）、`_ilt`（内联树根，759 行 `InlineTree::build_inline_tree_root()`）；
- `_barrier_set_state`（664）：`BarrierSetC2::create_barrier_state(comp_arena())`，GC 写屏障相关状态；
- NodeHash 预估 `code_size*4+64`、下限 1023（764-768，`MINIMUM_NODE_HASH`）。

`Init(bool aliasing)`（`compile.cpp:1045-1150`；**没有** `Initialize()` 方法）做全局准备：建 `RootNode` 与缓存的 top 节点（1071-1074）、在 env 侧挂三个记录器——`OopRecorder` / `DebugInformationRecorder` / `Dependencies`（1077-1079）、初始化 alias 表（1133-1149，`_max_alias_types=16`，`AliasIdxTop=1` / `AliasIdxBot=2` / `AliasIdxRaw=3`，`compile.hpp:228-231`）、读入一批编译策略参数（1099-1104：`_loop_opts_cnt = LoopOptsCount`、`_do_inlining = Inline`、`_max_inline_size`、`_freq_inline_size`、`_do_scheduling`）。

失败记账有三个层级，排查「某方法为什么没被 C2 编」时看它们：

| 机制 | 位置 | 语义 |
| :-- | :-- | :-- |
| `record_method_not_compilable` | 内联于 `compile.hpp:872-876` | 转调 `ciEnv::record_method_not_compilable` 后再 `record_failure`，方法被标记为不可编译 |
| `record_method_not_compilable_oom` | `compile.cpp:5348-5350` | 编译期内存超限（`CompilationMemoryStatistic` 给出原因串） |
| `check_node_count(margin, reason)` | `compile.hpp:877-888` | `live_nodes()+margin > max_node_limit()` 或 `oom()` 时置不可编译——**图爆炸的主要防线** |

## Ideal Graph

C2 的中间表示叫 **Ideal 图**：一组 `Node` 经数据边相连，控制流是显式的（`RegionNode` / `IfNode` / `CatchNode` 等），内存是显式的（`MemNode` 链）。

### Node

Node 从 Compile 的 node arena 分配，`operator delete` 是空实现（`node.hpp:267-274`）——**节点永不单独释放**，编译结束随 arena 整体回收。`Node::Init(int req)`（`node.cpp:292-315`）分配 `_idx`（`C->next_unique()`，`compile.hpp:893-895`），并按 required / precedence 两类切分输入数组（`node.hpp:321-337`）。

Node 的「相等」完全由 hash 表查找循环定义（`phaseX.cpp:86-94`）：先比 `req()` 与 `Opcode()`，再逐输入比**指针**，最后调 `n->cmp(*k)`：

```cpp
// node.cpp:1520-1530（节选）
uint Node::hash() const {
  uint sum = 0;
  for( uint i=0; i<_cnt; i++ )  // Add in all inputs
    sum = (sum<<1)-(uintptr_t)in(i);        // Ignore embedded nulls
  return (sum>>2) + _cnt + Opcode();
}
bool Node::cmp( const Node &n ) const {
  return true;                  // Must be same
}
```

基类 `cmp` 恒真，子类覆盖以加入「特殊位」比较（如 `ConNode` 的常量值）。**`Node::eq()` 已被移除**（`node.hpp:1299-1301` 只剩 `hash()` 与 `cmp()` 两个虚函数），旧文「hash 相等 && cmp==0 && eq」的三段式描述对 27 失效。

承载去重的 `NodeHash`（`phaseX.cpp:48-230`）就是**图的运行期 hash-cons 表**：开放寻址、相对素数步长、`_sentinel` 删除标记；`hash() == Node::NO_HASH`（即 0）的节点不进表（`phaseX.cpp:70-73`），`MergeMemNode` 就故意声明 `NO_HASH` / `cmp` 恒 false（`memnode.cpp:5827-5830`）——内存合并点不可 GVN 是 C2 的刻意设计。

### Node Families

Ideal 图的节点全集不是零散定义的，而是一张**集中登记的大表**：`classes.hpp` 的注释自称 "The giant table of Node classes. One entry per class, sorted by class name."（`classes.hpp:27-28`），jdk-27-ga 实测有 **511 个 `macro()` 条目**。`opcodes.hpp` 用宏把它们摊成 dense enum（`macro(x) Op_##x`，`opcodes.hpp:31-32`），并用 `_last_machine_leaf`（`opcodes.hpp:48`）把机器叶子寄存器与理想节点一刀切开，`NodeClassNames[]`（`opcodes.hpp:56`）提供 opcode 编号到名字的反查，打印与日志都靠它。

| 家族 | 代表 opcode（均取自 `classes.hpp`） | 职责 |
| :-- | :-- | :-- |
| 控制 | `Region` / `Phi` / `If` / `IfTrue` / `IfFalse` / `Jump` / `JumpProj` / `Goto` / `NeverBranch` / `Loop` / `CountedLoop` / `CountedLoopEnd` / `Root` / `Start` | 控制流与合并；投影节点 `Proj` / `CProj` 从 Region/If 上摘下具体出口 |
| 调用 | `CallJava` / `CallStaticJava` / `CallLeaf` / `CallLeafNoFP` / `CallLeafPure` / `CallRuntime` / `CallDynamicJava` | 都是 `CallNode`（`callnode.hpp:745`）子类，因而都是 SafePoint |
| 内存 | `LoadI` / `LoadL` / `LoadP` / `LoadN` / `LoadKlass` / `LoadRange` / `LoadVector` / `StoreI` / `StoreP` / `MergeMem` / `SCMemProj` / `MemBarRelease` | 显式内存链；load/store 按数据类型细分，`LoadNode`/`StoreNode` 本身是抽象类、没有独立 opcode |
| 安全点 | `SafePoint` / `Allocate` / `AllocateArray` / `Lock` / `ArrayCopy` / `BoxLock` / `Initialize` | 潜在去优化点，创建时统一挂 JVMState 链 |
| 常量与参数 | `ConI` / `ConL` / `ConP` / `ConF` / `ConD` / `ConN` / `ConNKlass` / `ThreadLocal` / `Parm` | 编译期常量与方法入口参数 |
| 算术与转换 | `AddI` / `AddL` / `MulL` / `SubI` / `AndI` / `OrI` / `XorI` / `ConvI2L` / `CastII` / `CastDD` / `CMoveI` / `AbsI` | 值计算，多数按 I/L/F/D 有四胞胎 |
| 机器相关 | `MachNode` / `MachProj` / `RegI` / `RegL` / `RegP` / `RegF` / `RegD` / `RegFlags` / `VecD` / `RegVectMask` | matcher 之后的 Mach 图世界；理想节点在此之后不再存活 |

> [!NOTE]
> **读图时的实用判据**：遇到不认识的 opcode，先回 `classes.hpp` 查它是否登记在案（表按类名字典序，好定位），再去对应的 `xxxnode.cpp` 找 `Ideal` / `Value` / `Identity` 三个虚函数——C2 每个节点的行为都分散在这三处加 `hash()`/`cmp()` 里，没有集中的「语义说明书」。

### Type

每个 Ideal 节点带一个 `Type`，构成编译期的类型格：`Type::meet_helper`（`type.cpp:1008-1029`）强制交换律与格对称性（DEBUG 下 `check_symmetrical` 验证 `meet(a,b) == dual(meet(dual(a),dual(b))`，`type.cpp:975-1005`），`join` 由对偶定义（`type.hpp:193-196`）。指针侧是 `TypePtr` → `TypeOopPtr` → `TypeInstPtr` / `TypeAryPtr` 家族（`type.hpp:1168/1352/1531/1640`）。

**speculative type（推测类型）在 27 是独立指针，不是位**：`TypePtr` 的 PTR 枚举（`type.hpp:1175`）里没有 `SPECULATIVE`，推测信息存在成员 `const TypePtr* _speculative` 与 `int _inline_depth`（`type.hpp:1196-1201`），配套 `remove_speculative`（`type.cpp:2751`）、`xmeet_speculative`（2802）、`hash_speculative`（2866）一套方法。这是 profile 驱动的类型推测（如「这个虚调用点的接收者 95% 是 ArrayList」）的载体，推测失效就走 uncommon trap 去优化。

### Memory Chain And Aliasing

内存访问不是 SSA 值，而是显式链：

- **load 按 alias 找 slice**：`GraphKit::make_load`（`graphKit.cpp:1622-1649`）先 `C->get_alias_index(type(adr))`（1630），取 `memory(adr_idx)`（1634）再建 `LoadNode::make`（`memnode.cpp:1014`）；
- **store 成为 slice 新头**：`store_to_memory`（`graphKit.cpp:1651-1682`）同样取 `memory(adr_idx)`（1662），`set_memory(st, adr_idx)`（1675）；
- 合并点的空 slot 回退 `base_memory()`（`MergeMemNode::memory_at`，`memnode.cpp:6072-6105`）。

alias 分类由 `Compile::find_alias_type`（`compile.cpp:1644-1772`）完成，判定入口是 `must_alias`（1804）与 `can_alias`（1822）——**load/store 消除、写屏障消除都建立在 alias 分析之上**。

## Parse

Parse 把字节码翻成 Ideal 图。**`Parse` 本身就是 `GraphKit` 的子类**（`parse.hpp:148`），构造即完成整方法建图：

```cpp
// parse1.cpp:417-419
Parse::Parse(JVMState* caller, ciMethod* parse_method, float expected_uses)
```

主流程（`parse1.cpp:461-669`）：`_iter.reset_to_method` → `init_blocks()`（导入 ciTypeFlow 的基本块与死代码信息）→ `build_exits()` → `create_entry_map()` → `do_method_entry()`（OSR 时改为 `load_interpreter_state`）→ `do_all_blocks()`（646，RPO 遍历）→ `do_exits()`。块内执行链是 `do_one_block()`（`parse1.cpp:1552`）→ `do_one_bytecode()`（`parse2.cpp:1985`）——后者是一个**纵贯数千行的大 switch**（从 `parse2.cpp:2007` 起，`graphKit.cpp:839` 的注释称之为 "the Big Switch in do_one_bytecode"）。

几个容易找错函数的点：

- **合并**在 `Parse::merge`（`parse1.cpp:1680`）→ `merge_common`（1731）：按需建 `RegionNode`（1772）、Phi 懒创建，内存合并走 `GraphKit::merge_memory`（`graphKit.cpp:2674`）。没有 `GraphKit::merge`。
- **死局部变量**：`kill_dead_locals`（`graphKit.cpp:830-868`）用 `method()->liveness_at_bci(bci())` 把死 local 置 top，减少 Phi 与 deopt 信息量。
- **异常**先攒状态再统一分发：`make_exception_state`（`graphKit.cpp:232`）生成带 ex_oop 的 SafePoint，`add_exception_state`（242-275）合并同类型同 sp 的异常，字节码边界由 `do_exceptions`（`parse1.cpp:945-969`）分派给 handler 或 `throw_to_exit`；`CatchNode` / `CatchProjNode` 在 `make_slow_call_ex` 中创建（`graphKit.cpp:2707-2713`）。

### SafePoint And Deopt Instrumentation

**Parse 期没有「插 SafePoint」这一步**：所有可能去优化的节点（call、allocate、lock、ArrayCopy）生来就是 `SafePointNode` 子类，创建时由 `add_safepoint_edges`（`graphKit.cpp:933-977`）统一挂 JVMState 链：`sync_jvms()`（947）记录 bci/sp → `clone_deep`（976）→ `set_jvms`（977）。JVMState 是用 `_caller` 串起来的内联链（`callnode.hpp:206-219`），输入边按 `| loc | stk | arg | mon | scl |` 布局（`callnode.hpp:235-236`）——「scl」段就是标量替换对象的字段。

编译期的每个假设都埋一个 **uncommon trap**：`GraphKit::uncommon_trap`（`graphKit.cpp:2157-2265`）把 `reason + action` 编码进 `trap_request`（2189-2190），action 会按**该 reason** 的历史重编次数降级——`too_many_recompiles(reason)` 为真且未显式要求保留动作时，`Action_maybe_recompile` / `Action_reinterpret` 被改成 `Action_none`（`graphKit.cpp:2196-2209`），C2 从此不再赌这个检查点。最终发一个调 `uncommon_trap_blob` 的调用（2262-2265）。插入点统计：`parse2.cpp` 11 处、`parse3.cpp` 4 处、`graphKit.cpp` 13 处、`library_call.cpp` 14 处——null check、range check、cast、profile poll、clinit barrier 各若干。去优化机制的完整展开见 [Deoptimization](/docs/CS/Java/JDK/JVM/Deoptimization.md)。

### On-Stack Replacement

C2 还有一种**不从方法入口开始**的编译：OSR（On-Stack Replacement）。解释器执行到循环回边发现它是热点，就带着当前帧的状态请求编译，编出来的 `nmethod` 只能从循环内部进入。`Compile` 用 `_entry_bci` 区分两种编译（`compile.hpp:307`，`is_osr_compilation()` 即 `_entry_bci != InvocationEntryBci`，`compile.hpp:587`）。

入口链与普通编译同一条，但 `CallGenerator` 是专用的：`CallGenerator::for_osr`（`callGenerator.cpp:291-297`）造一个带 OSR 标志的 `ParseGenerator`。它的注释特意警告：**传进来的 JVMState 是「正在执行中的方法」而不是调用者的**，因此这个 generator 不能与其他 generator 混用（`callGenerator.cpp:287-289`）。

Parse 到入口时分叉（`parse1.cpp:605-612`）：`is_osr_parse()` 为真时，entry map 的 `TypeFunc::Parms+0` 位置是一个指向 **OSR buffer** 的指针，随后调 `load_interpreter_state`（`parse1.cpp:183`）把解释器帧「倒灌」进 Ideal 图：

- **locals 区**：`off_heap_plus_addr(osr_buf, (max_locals-1)*wordSize)`（`parse1.cpp:273`）；
- **monitor 区**：`off_heap_plus_addr(osr_buf, (max_locals+mcnt*2-1)*wordSize)`（`parse1.cpp:222`），每把锁建一个 `BoxLockNode`，且强制 `set_coarsened()` / `set_unbalanced()`（235-236）——OSR 进来的锁不纳入编译期的锁分析；

## Profile-Driven Optimization

C2 的多数决策不是靠静态分析拍脑袋，而是靠解释器/C1 采集的 **MDO（Method Data）**。这些数据进入 C2 后主要变成三样东西：块频率、内联频率判据、谓词与推测检查。

**块频率估计**在 GCM 阶段完成：`PhaseCFG::estimate_block_frequency`（`gcm.cpp:1941`）。两条硬编码规则值得记住：

- **uncommon trap 所在的块强制判为 unlikely**——注释（`gcm.cpp:1941-1950`）解释得很直白：不是因为它相对频率低，而是因为踩一次就去优化，只会执行一次。判据是 `Block::has_uncommon_code()`（`block.hpp:361`），置频是 `uct->_freq = PROB_MIN`（`gcm.cpp:1998`）；
- **异常出口**天生低概率：`CatchProj` 的 fall-through 拿走 `1 - PROB_UNLIKELY_MAG(5)*_num_succs`，各异常出口平分剩下的 unlikely 份额（`gcm.cpp:2300-2306`）。

频率估计的下游消费者是块布局：`BlockLayoutByFrequency`（默认 true，`c2_globals.hpp:631`）经 `Compile::_do_freq_based_layout`（`compile.hpp:353`，访问器 642）打开频率驱动的 `PhaseBlockLayout`；raise/lower 的放置决策则容忍一个小的频率容差 `delta = 1 + PROB_UNLIKELY_MAG(4)`，避免因数值误差无谓 hoist（`gcm.cpp:1415`）。

Profile 还直接进入优化判据：内联的 `"low call site frequency"`（`bytecodeInfo.cpp:321`）、profiled loop predicate 的「路径频率 × 循环次数 ≥ 1」（`loopPredicate.cpp:1285-1286`）、以及 null check / class check / range check 等 speculative check 的插入，全部以 profile 为前提。

> [!WARNING]
> **与旧认知的差异**：`PrintCompilation` 日志里看到的频率是**编译期的估计值**，不是真实执行计数。profile 采错了不会让 C2 崩，但会产出「优化错了」的代码——此时兜底的不是重新分析，而是 uncommon trap 去优化。所以「profile pollution 导致性能回退」这类问题的正确排查方向是日志里的 deopt reason 与 trap action 变化，而不是频率数字本身。

`Compile::Code_Gen`（`compile.cpp:3043-3170`）把 Ideal 图变成机器码并安装，四段：**匹配 → 调度 → 寄存器分配 → 输出**。

### Matcher

`Matcher::match`（`compile.cpp:3058-3066` 调用，实现 `matcher.cpp:171-409`）做指令选择，核心是 `match_tree`（`matcher.cpp:1400-1471`）的三步：

```text
Label_Root         matcher.cpp:1548   DFA 标签化：ADLC 从 *.ad 生成的有限状态自动机匹配理想树
ReduceInst         matcher.cpp:1703   按最小 cost 的 State 项造 MachNode/MachOper（ADLC 生成的工厂）
Expand             matcher.cpp:1777   一个 MachNode 展开成多条指令（如 long 除法、调用序列）
```

`Matcher::find_shared`（`matcher.cpp:2027-2118`）后序遍历标记共享节点：同一节点第二次被访问到时 `set_shared(n)`（2043-2045），此后强制匹配进寄存器而非折叠进指令；`find_shared_node`（1651-1682）进一步让同一 `Con` 按相同 rule 复用 MachNode。`MaxLabelRootDepth` 下限 100（172）。

AD 文件（如 `x86_64.ad`）与 ADLC 不在本仓库检出范围内，机制上就是「树模式重写系统」：每条 instruct 规则给出理想树模式、cost 与机器指令模板，DFA 决定哪个子节点进寄存器、哪个被折叠。

### Global Code Motion

`PhaseCFG`（构造 `compile.cpp:3080`，`do_global_code_motion`@3086-3087）在 Mach 图上做全局调度（`gcm.cpp:1919-1937`）：`build_dominator_tree` → `estimate_block_frequency` → `global_code_motion`（1758-1917）：

```text
schedule_pinned_nodes          1774   控制/固定位置节点先入块
schedule_early                 1781   raise：把节点抬到可放置的最早块
compute_latencies_backwards    1793   反向算 latency（do_scheduling 开启时）
schedule_late                  1801   lower：放到 LCA 且循环深度最浅的块
schedule_local                 1879   块内"简单拓扑排序"（定义在 lcm.cpp:956）
call_catch_cleanup             1898   Call 与 CatchNode 之间插入指令的修补
```

C2 其实有**三次调度**：GCM 的 raise/lower（RA 前）、GCM 末尾的块内拓扑排序、以及 RA 之后 Output 阶段的 latency 感知 `ScheduleAndBundle`（`output.cpp:2026`）。`OptoRegScheduling`（x86 默认 **true**，`c2_globals_x86.hpp:62`）会在 GCM 里跑一遍临时 RA 只为计算寄存器压力（`gcm.cpp:1837-1871`）。

### Block Ordering And Peephole

### Debug Information And Oop Maps

RA 之后、`fill_buffer` 之前，`PhaseOutput::BuildOopMaps`（`buildOopMap.cpp:605`）为每个 safepoint 计算 **oop map**：先按块做反向活跃性分析（`do_liveness`），再逐块传播 `OopFlow`（`compute_reach` / `merge` / `clone` 分别在 110 / 167 / 185），最后 `OopFlow::build_oop_map`（209）把寄存器与栈槽里的活引用列成表。safepoint 的 pc 偏移与 oop map 在 `fill_buffer` 里配对登记：`C->debug_info()->add_safepoint(pc_offset, oop_map)`（`output.cpp:993/1006`）。

与 oop map 登记在一处的还有**帧的调试信息**（`output.cpp:1158-1190`）：

- `create_scope_values(locarray)` / `create_scope_values(exparray)` / `create_monitor_values(monarray)`（1161-1163）分别序列化 locals、表达式栈与 monitor 三段；
- `describe_scope(...)`（1173）把一段 scope 与 bci/内联深度绑定，`end_safepoint`（1190）收尾；
- 非 safepoint 位置也记录纯行号信息（`recording_non_safepoints()`，1211）——这就是编译后的代码仍能给出准确 Java 行号栈帧的原因。

去优化时帧的恢复靠的就是这两样：oop map 告诉 GC/线程扫描哪些位置是引用，scope values 告诉 runtime 每个局部变量与 monitor 的当时值；被标量替换的对象靠 JVMState 的 scl 段（`callnode.hpp:235-236`）携带字段，由 runtime 侧重建（见 [Deoptimization](/docs/CS/Java/JDK/JVM/Deoptimization.md)）。

> [!WARNING]
> **与旧认知的差异**：`ReplacedNodes`（`replacednodes.hpp:44`）**不是**「标量替换对象的调试信息」。它的头注释（`replacednodes.hpp:30-43`）写得很清楚：这是 Parse 期 `GraphKit::replace_in_map` 的传播机制——每个 `SafePointNode` 携带一份「本路径上被改进的节点对」，控制流合并时跟着合并（`merge_replaced_nodes_with`，`graphKit.cpp:446`），方法出口时回写调用者的 map（`callGenerator.cpp:896-897/963`）。名字里的 replaced 指「节点被替换」，与 EA 的 scalar replacement 毫无关系。

### Install

`PhaseOutput::install`（`output.cpp:3168`）：`should_install_code()` 为假（`RepeatCompilation` 演练）时直接返回；stub 走 `install_stub` → `RuntimeStub::new_runtime_stub`（3245）；方法走 `install_code`（3182）→ `C->env()->register_method(...)`（3211），把 CodeOffsets、frame size、oop maps、handler table 一并交给编译环境层去分配 `nmethod` 并注册进 CodeCache。**deopt handler 不是 C2 装的**：去优化靠 uncommon trap + safepoint 的 debug info/oop map，反优化由 runtime 完成（见 [Deoptimization](/docs/CS/Java/JDK/JVM/Deoptimization.md)）。

## Bailout And Deopt

C2 的失败分三类，日志里能看到对应痕迹：

1. **图超限**：`check_node_count`（`compile.hpp:877-888`）在 `live_nodes()+margin > max_node_limit()`（默认 `MaxNodeLimit`=80000，`c2_globals.hpp:517`）或编译期 OOM 时置不可编译；`compile.cpp:3072` 在匹配后再查一次（"out of nodes matching instructions"）。
2. **策略降级**：入口的重试阶梯（见上）跑完后仍失败，`env->record_failure` 兜底（`c2compiler.cpp:197`）。
3. **不可逆失败**：早已经 `env->record_method_not_compilable()` 记录（`c2compiler.cpp:194-196` 注释），方法后续不再送 C2。

从 opto/ 源码统计（jdk-27-ga，剔除注释行后 grep 计数），C2 侧埋点最多的去优化原因是：

| DeoptReason | 出现次数 | 典型场景 |
| :-- | :-- | :-- |
| `Reason_intrinsic` | 25 | intrinsic 的 speculative check 失败 |
| `Reason_unstable_if` | 11 | profile 不稳定的分支（`process_for_unstable_if_traps`） |
| `Reason_range_check` | 10 | 数组/字符串下标检查 |
| `Reason_class_check` | 10 | 类型检查（cast、instanceof） |
| `Reason_predicate` | 9 | loop predicate |
| `Reason_profile_predicate` | 9 | profiled loop predicate |
| `Reason_loop_limit_check` | 9 | 计数循环的 limit 检查（`graphKit.cpp:4175`） |
| `Reason_auto_vectorization_check` | 8 | 向量化运行时检查 |
| `Reason_short_running_long_loop` | 8 | 「长循环但总执行短」的判定（`graphKit.cpp:4163`） |
| `Reason_null_check` | 7 | 推测非空失败 |

完整的 `DeoptReason` 枚举与 `Action_*` 取值在 runtime 层（`deoptimization.hpp`，不在 opto 检出内）；日志里 `deoptimization` 事件带的 reason 字符串与上表一一对应，排性能问题时按出现次数从高往低查即可。

无论哪种，方法都回退到解释器或已有低层编译版本继续执行（入口分派见 [ExecutionEngine](/docs/CS/Java/JDK/JVM/ExecutionEngine.md)），**不会让应用崩掉**——这也是 C2 敢做激进优化的前提：任何推测破产都有一条「退回解释帧」的路（[Deoptimization](/docs/CS/Java/JDK/JVM/Deoptimization.md)）。
