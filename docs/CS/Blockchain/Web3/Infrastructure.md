## Introduction

一个自称"去中心化应用"的产品，实际运行时依赖的远不止那条链：钱包要读链得连 RPC，前端要显示历史得查索引器，图片与元数据存在内容寻址网络上，价格与随机数来自预言机，跨链资产要经过桥。**这些链下环节往往比链本身更中心化**。

这是 Web3 最容易被忽视、也最值得逐项盘点的一层。判断一个应用是否真的去中心化，不能只看它的合约是否开源，而要看它的每一条外部依赖是否可替换。链本身的扩展方案见 [Layer 2](/docs/CS/Blockchain/Layer2.md) 与 [Architecture](/docs/CS/Blockchain/Architecture.md)。

## RPC Layer

绝大多数用户并不运行节点：钱包和 DApp 通过 JSON-RPC 访问链，服务商承担了节点运维、索引、缓存与限流。

- **中心化 RPC 服务商**：开箱即用、稳定、带增强 API，代价是它们能看到你的 IP 与全部查询内容，可以限流、审查或记录行为；
- **公共 RPC**：免费但限流严格、可用性无保障，适合测试不适合生产；
- **去中心化 RPC 网络**：用代币激励把请求路由到多个独立节点运营商，提升抗审查性，但延迟与一致性通常弱于中心化服务；
- **自建节点**：唯一真正去信任的方式，成本是运维与硬件。

一个常被忽略的细节：`eth_getLogs` 等查询有返回条数上限，历史数据可能因为节点裁剪而不完整。这意味着**"链上数据公开可查"不等于"你随时能低成本查到"**，数据可得性本身是基础设施提供的服务。

## Indexing

链的存储结构是"按区块追加"，为写入优化，不适合查询。"某个地址过去一年在某合约里的所有操作"这类问题，靠遍历区块几乎不可行，因此需要索引层：

- **事件日志（Logs）**：合约主动抛出的结构化记录，是索引的主要原料。日志便宜但**不能被合约自己读取**，只能给链下消费；
- **索引器**（如 The Graph 的 subgraph）：定义"监听哪些事件 → 写入哪些实体"，把链上事件物化成可查询的 API；
- **信任问题**：索引器输出的结果不由共识保证。前端显示的余额、排名、历史，正确性依赖索引器实现与运维方。若索引 disclosed 被污染或滞后，用户看到的就是错的；
- **缓解**：关键数据（如清算状态）应从合约直接读取或要求 Merkle/状态证明，而不是信任索引器。

## Storage

把图片与元数据放到链上极其昂贵，因此实际存储在别处，链上只存一个哈希或 URI：

| 方案 | 模型 | 持久性来源 | 适用 |
| --- | --- | --- | --- |
| IPFS | 内容寻址（CID），按需取回 | **需要有人 pin**。没人 pin，数据就会消失 | 可复制的公共内容、前端静态资源 |
| Filecoin | 存储证明（复制证明 + 时空证明） | 与矿工签订存储合约，到期需续约 | 需要可验证存储承诺的数据 |
| Arweave | 一次付费、长期保存 | 前期费用进入存储基金，靠利得覆盖成本 | 一次性归档、需要长期可取的资料 |

"上链"这个词在存储场景下经常是误导：**NFT 的图通常不在链上，链上只有一段指向图的位置**。若该位置托管在中心化服务器或无人 pin 的 IPFS 上，资产的持久性就取决于某个运营方是否持续付费。给 NFT 估值时，检查元数据与媒体的存放方式是可验证的一环，见 [DeFi and NFT](/docs/CS/Blockchain/Web3/DeFi_and_NFT.md)。

## Oracles

合约无法主动发 HTTP 请求，且必须保持确定性，因此链下数据需要由预言机写入：

- **价格馈送**：多个数据源聚合后定期更新，是借贷与衍生品的生命线。风险集中在**更新频率、数据源质量与更新权限**；
- **可验证随机数（VRF）**：提供链上可验证的随机输出，用于抽奖、游戏与排序；
- **储备证明（Proof of Reserve）**：把链下资产（如稳定币储备）的余额喂到链上；
- **跨链消息**：把一条链的状态证明传递到另一条链，见下文桥的部分。

预言机是**明确且不可消除的信任点**：它决定了协议何时认为你该被清算。评估预言机时要看偏离阈值（偏离多少才更新）、心跳间隔、数据源数量，以及是否存在单笔交易内操纵的可能（用低流动性池的即时价格做预言机是经典事故）。

## Bridges

跨链是损失最集中的环节，原因在于它把两条链的安全假设绑在了一起：

| 模型 | 机制 | 信任假设 |
| --- | --- | --- |
| 锁仓-铸造 | 源链锁仓，目标链铸造映射资产 | 信任托管方/验证者集合；被攻破则映射资产失去背书 |
| 流动性网络 | 两侧资金池，做市商垫付再结算 | 信任流动性提供者与撮合逻辑，容量受池深度限制 |
| 轻客户端桥 | 目标链验证源链共识 | 信任源链共识，安全性最高，成本高 |
| 消息层 | 通用跨链消息传递，上层再建应用 | 信任消息层的验证者集合 |

使用桥的安全原则是：**把它当作有到期日的信任，而不是基础设施**。跨完就走，不要在桥里长期存放资产；优先选择能做有效性证明的方案；大额跨链要考虑分批与等待期。桥的攻击面与历史事件见 [Security](/docs/CS/Blockchain/Security.md)。

## Sequencing and Data Availability

用户的交易由谁排序、数据存在哪里，决定了 L2 的实际信任模型：

- **排序器（Sequencer）**：多数 Rollup 目前由单一运营方排序，带来快速确认与抗 MEV 的可能，也带来审查与单点故障。缓解手段是强制提现（用户绕过排序器直接向 L1 提交）与故障/有效性证明；
- **数据可用性**：Rollup 必须让任何人能拿到重建状态所需的数据。EIP-4844 引入 blob 作为廉价的数据发布空间；Fusaka 升级（2025 年 12 月 3 日激活）用 PeerDAS（EIP-7594）让节点通过采样而非全量下载来验证数据可用性，并通过"仅调整 blob 参数"的 BPO 分叉逐步提升每个区块的 blob 上限（从 6/9 提升至 10/15，再到 14/21）；
- **预确认**：为了让用户不必等一个完整区块，出现由出块方提前承诺打包的服务。它改善了体验，也把"确认"的含义从"已经在链上"变成了"有人承诺会放进去"。

## Frontend and Delivery

合约不可变，但用户接触的前端是可变的：

- **中心化托管**：绝大多数 DApp 前端跑在云与 CDN 上，域名或账户被封、DNS 被劫持、构建被投毒，用户就会访问到假界面；
- **替代路径**：前端部署到 IPFS/Arweave，配合 ENS 名称与内容哈希，使用户可通过"名字指向哪个内容哈希"验证版本；也可让用户直接调用合约（命令行或区块浏览器的写入接口）；
- **供应链风险**：前端依赖的 npm 包、CDN 脚本、钱包 SDK 都是攻击面，历史上的大额盗损有相当比例来自前端被注入恶意代码而非合约漏洞。

合约安全不等于产品安全：**用户签什么，由前端决定**。这一点无法通过审计合约来解决。

## Trust Map

把所有依赖列出来逐项打分，比争论"是否去中心化"有用得多：

| 层 | 典型依赖 | 失败后果 | 可替换性 |
| --- | --- | --- | --- |
| 共识与结算 | L1 验证者集合 | 双花、重组 | 换链 |
| 执行与排序 | L2 排序器 | 交易被审查、服务中断 | 强制提现、换 L2 |
| 数据可用性 | blob / DA 层 | 状态无法重建 | 换 DA 方案 |
| 访问层 | RPC 服务商 | 无法读链、隐私泄露 | 自建节点、换服务商 |
| 查询层 | 索引器 | 前端数据错误 | 自建索引、直读合约 |
| 资产与价格 | 预言机 | 错误清算、错误定价 | 多源聚合 |
| 跨链 | 桥 | 资产失去背书 | 换桥、避免长期存放 |
| 资金入口 | 稳定币发行方 | 地址被冻结、无法赎回 | 换计价单位 |
| 界面 | 前端托管与依赖 | 钓鱼、假界面 | IPFS + ENS、直连合约 |
| 账户 | 钱包、bundler、paymaster | 无法使用、被审查 | 换钱包、自托管 bundler |

**结论式用法**：这张表里的每一行，都是一个"如果它作恶或宕机，会发生什么"的问题。能答出来，才算真正理解了这个应用的去中心化程度。
