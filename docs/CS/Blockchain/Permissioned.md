## Introduction

联盟链（consortium blockchain）与私有链（private blockchain）把"无准入"换成"受控成员"，用身份、权限与 BFT 共识换取确定性最终性、吞吐与隐私。它们不发行代币，也不依赖算力或质押激励，适合**多个已知机构共享一份账本，但不愿把数据交给单一中心**的场景。

判断是否需要联盟链，核心问题不是"要不要用区块链"，而是**参与方之间是否真的存在互不信任、又必须共同维护同一份历史的关系**。如果没有，中心化数据库 + 审计日志通常更便宜。

## Permission Models

联盟链的准入通常分三层：

- **网络准入**：哪些节点可以接入，由证书或白名单控制；
- **交易准入**：谁可以提交交易、调用哪些链码，由身份与策略决定；
- **数据准入**：谁可以看见哪些数据，由通道、私有数据集合或交易隐私机制控制。

身份是联盟链的一等公民：成员有真实组织身份，行为可追责，这与公链的伪匿名模型根本不同。代价是**治理与准入规则必须显式设计**，否则联盟会退化成"几家大机构的多签数据库"。

## Hyperledger Fabric

Fabric 是最主流的联盟链框架，架构与公链差异很大：

- **执行-排序-验证（execute-order-validate）**：交易先在背书节点模拟执行并签名，再交给排序服务定序，最后提交节点验证背书策略与读写集冲突。这与公链"先排序、再执行"相反，目的是把执行并行化并支持非确定性语言；
- **Peer**：维护账本与状态数据库（LevelDB/CouchDB），执行链码，根据背书策略背书；
- **Orderer**：排序服务，默认 Raft（崩溃容错），Fabric v3.0 引入 SmartBFT 支持拜占庭容错排序；
- **Channel**：一条通道是一条独立账本，只有通道成员可见，天然实现数据隔离；
- **Chaincode**：链码（Go/Java/Node.js），可运行在 Docker 容器或作为外部服务；
- **MSP / Fabric CA**：成员服务提供者管理证书与身份，CA 签发注册证书；
- **Private Data Collection（PDC）**：敏感数据只发给授权节点，链上只存哈希，兼顾隐私与可验证性；
- **背书策略**：如"3 个组织中至少 2 个签名"，决定交易有效性。

Fabric 的强项是**许可治理、通道隔离与企业级运维**；弱项是链码生态、跨链互操作与开发体验。v2.5 是 LTS 版本，v3.0 引入 BFT 排序，适合对排序服务也有拜占庭容错要求的联盟。

## Hyperledger Besu and Quorum

- **Besu**：以太坊客户端，可作为许可链节点运行，支持 QBFT、IBFT 2.0 等 BFT 共识，以及基于节点的许可控制；
- **Quorum**：早期基于以太坊的联盟链方案，后被 ConsenSys 收购并并入 Besu 生态，私有交易能力逐步由其他隐私方案替代；
- **优势**：复用 EVM、Solidity 与以太坊工具链，迁移成本低；
- **取舍**：EVM 的公开状态模型与联盟链的隐私需求存在张力，隐私通常需要额外组件。

如果团队已有以太坊开发经验，Besu/QBFT 往往是比 Fabric 更低的学习成本选择；如果需要强隐私与通道隔离，Fabric 更合适。

## Corda

Corda 的设计目标不是"全球共享账本"，而是**点对点共享事实**：

- **State**：账本状态，只在相关方之间共享，不广播给全网；
- **Contract**：验证状态转换的规则（JVM 代码）；
- **Flow**：定义多方交互协议，节点之间直接通信；
- **Notary**：只负责防止双花与确认唯一性，不看到交易内容；
- **隐私**：默认只有交易参与方知道交易，天然适合金融合约；
- **Corda 5**：面向企业部署的版本，强调互操作与云原生。

Corda 更接近"分布式合同平台"而非"区块链"，适合贸易融资、保险、证券结算等需要强隐私与法律确定性的场景。

## Other Platforms

- **FISCO BCOS**：国内开源联盟链，PBFT 类共识、并行执行、隐私保护，常用于政务与金融试点；
- **Hyperledger Sawtooth**：早期联盟链框架，已进入维护/归档状态，新项目不建议选择；
- **蚂蚁链、腾讯云区块链**：云厂商托管的联盟链服务，降低运维门槛但增加供应商锁定；
- **CBDC 与批发结算**：多国央行试点使用许可链做跨境支付与结算，强调合规、隐私与最终性。

选型时不要只看 TPS 宣传，更要看治理模型、隐私能力、运维成熟度、社区活跃度与退出成本。

## Trade-offs

| 维度 | 公链 | 联盟链 |
| --- | --- | --- |
| 准入 | 无许可 | 身份与证书 |
| 共识 | PoW/PoS，概率/经济最终性 | BFT，确定性最终性 |
| 吞吐 | 低（L1） | 千级 TPS |
| 延迟 | 秒到分钟 | 亚秒到秒 |
| 隐私 | 默认公开 | 通道、PDC、点对点 |
| 激励 | 代币 | 联盟治理与商业契约 |
| 升级 | 社区分叉 | 联盟投票 |
| 信任 | 多数资源/权益 | 联盟多数成员 |
| 成本 | gas + 共识成本 | 联盟运维成本 |

联盟链的本质是**用治理换性能与隐私**。它的去中心化程度有限，安全性依赖联盟成员的诚实多数；一旦联盟内部出现利益冲突，治理机制比共识算法更关键。

## Use Cases

- **供应链金融**：应收账款、仓单、核心企业信用在多级供应商之间流转；
- **贸易融资**：信用证、提单、跨境结算的多方共享与核验；
- **存证与司法**：电子合同、版权、医疗记录的哈希锚定与审计；
- **政务数据共享**：跨部门数据交换，权限与审计可追溯；
- **碳交易与能源**：绿证、碳配额的登记与流转；
- **跨境支付**：多边央行数字货币桥、批发结算。

成功的联盟链项目通常有一个**强势的联盟发起方**推动成员接入，并解决真实的跨机构对账问题；失败的项目往往只是把中心化系统换个"链"的名字。

## Design Checklist

1. **成员与治理**：谁有准入权、谁决定升级、争议如何解决？
2. **信任边界**：哪些数据必须共享、哪些必须隔离？
3. **共识选择**：Raft 足够，还是需要 BFT？成员是否可能作恶？
4. **隐私方案**：通道、私有数据集合，还是点对点共享？
5. **性能目标**：峰值 TPS、延迟、账本增长与归档策略；
6. **身份体系**：证书、密钥、角色、吊销与轮换；
7. **互操作**：是否需要与公链、其他联盟链或传统系统对接？
8. **退出机制**：成员退出、数据迁移、系统停运时资产与记录如何处理？
