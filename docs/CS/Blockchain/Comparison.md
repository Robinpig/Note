## Introduction

区块链常被当作"更安全、更去中心化的数据库"推销，但两者解决的是不同问题。**数据库优化的是在信任边界内高效读写；区块链优化的是在信任边界外就写入顺序与历史达成一致。** 选错工具的代价很直接：用链做普通业务系统会得到几十 TPS、不可改数据、难以升级的架构；用中心化数据库做多方对账则要长期承担对账、审计与单点作恶风险。

这一页给出选型判据、三种链形态的差异，以及常见的"不该上链"清单。

## Blockchain vs Distributed Database

| 维度 | 分布式数据库 | 公链 | 联盟链 |
| --- | --- | --- | --- |
| 写权限 | 运营方授予 | 任何人 | 联盟成员 |
| 信任假设 | 信任运营方或已知副本 | 不信任任何单一主体 | 信任联盟治理与多数成员 |
| 吞吐 | 万级到百万级 TPS | 个位到几十 TPS（L1） | 千级 TPS |
| 延迟 | 毫秒级 | 秒到分钟级 | 亚秒到秒级 |
| 最终性 | 通常即时/强一致 | 概率或经济最终性 | BFT 确定性最终性 |
| 数据修改 | 可 UPDATE/DELETE | 只能追加，纠错靠新交易 | 受策略约束，通常也追加 |
| 查询能力 | 丰富（join、聚合、索引） | 极弱，需索引器 | 中等，受链码限制 |
| 隐私 | 访问控制 | 默认全公开 | 通道/私有数据集合 |
| 升级 | 运营方决定 | 分叉与治理，极难 | 联盟投票 |
| 成本 | 硬件与运维 | gas/手续费 + 共识成本 | 联盟运维成本 |

结论可以压缩成一句话：**如果所有写者都信任同一个运营方，用数据库；如果写者互不信任且必须共享同一份历史，才考虑链。**

## Public vs Consortium vs Private

### Public Blockchain

- 无准入，匿名或伪匿名参与，靠代币激励维护安全；
- 安全模型是"多数资源/权益不作恶"，最终性依赖概率或经济罚没；
- 适合需要公开可验证、抗审查、跨组织的场景：支付、DeFi、NFT、公共存证、身份凭证的锚定层；
- 代价：性能低、隐私差、交易成本随拥堵波动、治理分散且升级缓慢。

### Consortium Blockchain

- 准入受控，成员身份已知，通常由多家机构共同治理；
- 用 BFT 类共识（PBFT 变体、Raft 用于崩溃容错）获得确定性最终性与较高吞吐；
- 数据可按通道或私有集合隔离，适合商业敏感数据；
- 适合供应链金融、贸易融资、跨境支付、票据、政务数据共享、行业联盟存证；
- 代价：本质是"多方共治的分布式系统"，去中心化程度有限，治理与准入规则的设计比技术更难。

### Private Blockchain

- 单一组织控制，节点准入与共识都由该组织决定；
- 技术上有链式结构与智能合约，但信任模型与中心化数据库无异；
- 真实价值通常在于**审计留痕、不可否认、内部多部门对账**，而非"去信任"；
- 如果只是为了不可篡改日志，带哈希链的审计日志 + WORM 存储往往更划算。

## Decision Checklist

在动手之前逐条回答，任何一条答"否"都应重新考虑：

1. **是否存在多个互不信任的写入方？** 只有一个写入方时，链没有意义。
2. **是否必须共享同一份历史，而不是各自记账后对账？** 如果对账成本可接受，传统系统更简单。
3. **参与方是否愿意共同维护治理规则？** 链的升级、准入、争议处理都需要治理机制。
4. **业务能否接受最终性延迟与不可回滚？** 支付、清算能接受秒级到分钟级；高频交易不能。
5. **数据能否公开或至少对联盟成员可见？** 全公开不现实时，需要通道或隐私方案。
6. **吞吐与成本是否匹配？** 公链 L1 的 TPS 与手续费决定了它只适合"高价值、低频率"的写入。
7. **监管与合规是否允许？** 代币、跨境资金、数据出境都有额外约束。

## When Not to Use Blockchain

- **单写入方系统**：内部订单、库存、CMS，数据库加审计日志足够；
- **超高频写入**：广告竞价、行情撮合、IoT 遥测，链的复制与共识成本不可接受；
- **需要频繁修改或删除的数据**：GDPR 的删除权与不可篡改天然冲突，只能用链下存储 + 链上哈希锚定；
- **强隐私场景**：医疗、个人征信，公链默认公开，联盟链也需额外隐私设计；
- **参与方少于三个且互相信任**：直接用共享数据库或 API；
- **只是想要"区块链"概念背书**：没有多方信任问题，链只会增加复杂度与成本。

## Hybrid Patterns

现实中更常见的是混合架构，而不是"全上链"：

- **链上锚定 + 链下数据**：把文件哈希、Merkle 根写到链上，原始数据留在对象存储，兼顾成本与可验证性；
- **链上结算 + 链下执行**：Rollup、状态通道、链下撮合 + 链上清算，见 [Layer 2](/docs/CS/Blockchain/Layer2.md)；
- **联盟链 + 公链锚定**：联盟内部高频交易，定期把状态根锚定到公链以获得外部可验证性；
- **数据库 + 哈希链审计**：不追求多方共识，只追求事后不可抵赖，成本最低。

## Migration and Operations

上链不是一次性动作，运维成本常被低估：

- **密钥管理**：机构需要 HSM、多签、权限分离，私钥丢失等于资产丢失；
- **节点运维**：全节点、归档节点、RPC 网关、监控与告警；
- **升级路径**：合约可升级性（代理模式）与治理流程必须提前设计，见 [Smart Contract](/docs/CS/Blockchain/SmartContract.md)；
- **合规审计**：交易可追溯是优点也是负担，需要与法务、风控流程对接；
- **应急响应**：暂停、熔断、资金迁移预案，桥与合约事故往往以小时计。
