## Introduction

对话系统（dialogue system）是自然语言处理里少见的「综合体」：它必须同时完成理解（听懂这轮说了什么）、状态维护（这句话之后我们进行到哪一步）、策略决策（下一步该说什么、该做什么）与生成（把动作说成人话）四项工作，任何一环掉链子都会在用户侧直接暴露。它也是唯一一个「评估比任务本身更难」的领域——翻译、分类、抽取都有相对客观的参考答案，而一段对话好不好，往往连人类标注者之间都难以取得一致。本文讨论对话系统的三类形态、任务型系统的经典管线、方法演进、开放域对话的特殊问题，并把评估单独展开，因为它才是这个方向真正的瓶颈。

## Three Types of Dialogue Systems

按目标划分，对话系统分三类。

**任务型（task-oriented）**系统有明确的达成目标：订票、查询账单、客服工单处理。判断成功的标准是「任务是否完成」，而不是「聊得是否愉快」。这类系统可以定义状态与动作，因此能被建模为序列决策问题，也是学术研究里最系统化的一支。

**开放域闲聊（open-domain chit-chat）**没有外部目标，价值在于维持一段有信息量、有一致性的对话本身。目标模糊直接导致评估困难：没有任务完成率可用，只能依赖人工判断，而人工判断的成本与可复现性问题贯穿整个方向。

**混合助手**在现代产品里最常见：既能闲聊，又能查天气、订餐、执行操作。此时的「任务部分」本质上接近问答与工具执行，对应本库的 [QuestionAnswering](/docs/CS/AI/NLP/QuestionAnswering.md) 与 [Agent](/docs/CS/AI/LLM/Agent/Theory/Agent.md) 两条线，本文不重复展开，只关注对话层面的组织问题。

三类的差异可以用一张表对齐：

| 类型 | 目标 | 成功标准 | 主要评估方式 |
| :--- | :--- | :--- | :--- |
| 任务型 | 完成具体事务 | 任务是否达成 | 任务完成率、轮数、槽位准确率 |
| 开放域闲聊 | 维持对话本身 | 体验是否自然、有内容 | 人工判断为主 |
| 混合助手 | 两者兼有 | 任务达成 + 体验 | 任务指标 + 人工抽检 |

## The Classic Task-Oriented Pipeline

经典任务型系统的管线由四个模块串成：

| 模块 | 全称 | 职责 |
| :--- | :--- | :--- |
| NLU | natural language understanding | 意图识别（intent detection）+ 槽位填充（slot filling） |
| DST | dialogue state tracking | 维护对话状态：已确认的槽位、待确认的假设、历史动作 |
| DP | dialogue policy | 决定下一步动作：追问缺失槽位、确认、执行、结束 |
| NLG | natural language generation | 把动作转成回话（模板或神经生成） |

数据在管线里的流向是单向的：用户话语进 NLU 变成结构化表示，DST 把它并入状态，DP 依据状态选动作，NLG 再把动作渲染成回话。每一环的输出都是下一环的唯一输入，这也决定了错误只能被放大、无法被下游纠正。

**管线式的优点是可控**：每一步都能单独评估、单独替换，出错时可定位到具体模块，这对线上客服这类需要审计的场景非常重要。**缺点是误差传导与模块割裂**：NLU 识别错的槽位会污染状态，状态错会导致策略选错动作，NLG 再流畅也救不回来；而且四个模块各自优化自己的局部目标，与「整段对话成功」并不等价。后来的端到端与强化学习方法，很大程度就是针对这两个缺点提出的。

### State Tracking as the Bottleneck

四个模块里，DST 的工程难度最容易被低估。它要回答的是「此刻我们已知什么、还缺什么、哪些信息可信」，而这些判断往往并不显式出现在字面上：用户可能中途改口（先说「周五」又说「算了还是周六」），可能用代词跨轮指代（「就订那个吧」），也可能在一个句子里同时给出新信息与确认旧信息。多轮对话的上下文越长，这些隐式修改越难追踪，状态一旦错位，后续的追问与执行就会连环出错。

因此 DST 的经典做法会在「状态假设」上做文章：不只记录已确认的槽位，还记录候选值与置信度，用确认（confirm）动作向用户逼近真实意图。这也解释了为什么任务型对话的轮数往往降不下来——大量回合消耗在「把状态对齐」而不是「把事情做完」上。

## Method Evolution

方法脉络可以按「优化的是什么」来划分：规则优化字符串匹配，监督学习优化下一句的似然，强化学习优化整段对话的回报，大模型则把优化外包给预训练与提示。

### Template and Rule-Based Bots

最早的工业实现是模板与规则：匹配关键词与正则，命中即回复。它在上线成本与可控性上至今仍有优势（很多金融、政务机器人仍是这种形态），但泛化能力极差，稍微换个说法就失效。

### Supervised End-to-End

[Learning End-to-End Goal-Oriented Dialog](https://arxiv.org/abs/1605.07683) 把对话当作序列学习问题：不再显式维护状态与策略，而是让模型直接从对话历史映射到回复。这类方法证明了端到端可行，也暴露出数据饥饿与难以注入业务约束的问题——纯监督学习的目标是「模仿训练集里出现过的下一句」，而不是「把任务做成」。

### Reinforcement Learning for Strategy

[Deep Reinforcement Learning for Dialogue Generation](https://arxiv.org/abs/1606.01541) 把优化目标从单步似然换成回报：一轮回复的好坏不再只看它像不像语料，而要看它把对话推向了什么结果（成功、轮数、是否陷入死循环）。这解决了监督学习的短视问题，但也引入了新的难题——回报稀疏、奖励设计本身成为研究议题、在线探索在真实用户面前代价高昂。工程上常见的折中是离线用 RL 或规则做策略，线上做安全兜底。

### LLM Unifies the Four Modules

大语言模型的路径完全不同：不再拆模块，而是把对话历史、可用工具、业务约束一起写进上下文，用一个提示统一完成理解、状态推断、动作选择与表达。**工具调用（tool calling）本质上就是槽位与动作的现代形态**——模型输出的结构化参数即 NLU 与 DST 的结果，调用哪个工具即 DP 的决策。这一路线的代价是把可控性从「模块接口」转移到了「上下文与评估」，如何约束与验证模型的行为成为新的工程主题，具体机制转 [LLM](/docs/CS/AI/LLM/LLM.md)。

延伸阅读可见 [A Survey on Dialogue Systems: Recent Advances and New Frontiers](https://arxiv.org/abs/1711.01731)：这是 2017 年的综述，覆盖的正是「深度学习时代」的方法谱系，任务型、开放域与强化学习三条线都有系统梳理。

## Open-Domain Dialogue

开放域对话既没有状态可维护，也没有回报可定义，因此研究焦点落在建模方式与体验质量两个问题上。

### Retrieval vs Generation

**检索式（retrieval-based）**从候选语料里挑一条最合适的回复：质量稳定、不会产生语法错误，但受限于语料覆盖，遇到语料里没有的场景只能给出泛泛的回应。**生成式（generative）**用序列到序列模型直接生成回复，泛化面更广，代价是可控性差、容易产生事实错误与不当内容。工程上常见「检索保底 + 生成润色」的混合策略：先用检索保证回复安全、相关，再让生成模型组织措辞。

### Safety, Consistency and Diversity

生成模型的三个典型病灶。**安全**：可能输出有毒内容，且触发条件难以穷举。**一致性**：人设会在多轮里漂移（前面自称某身份，几轮后自相矛盾），而人格一致性恰恰是闲聊体验的核心。**多样性**：以最大似然为目标训练出的模型倾向于生成「我不知道」「这个问题很有意思」这类高概率安全回复——它们在似然上得分高，在人类偏好上得分低，与评估指标之间存在系统性偏差。

## Evaluation

对话评估的困难程度超过任务本身，值得单独展开。可按评估粒度分三层，每层回答不同的问题，也各有盲区。

### Turn-Level Metrics

轮级指标只看单轮回复的质量。这里要先明确一个否定结论：**BLEU、困惑度（perplexity）这类指标在对话上并不适用**。它们衡量的是与参考文本的表面重合或语言模型的拟合程度，而对话里一句回复有大量同样合理的说法，与参考不重合不代表质量低；反过来，高似然的回复常常正是那些无信息量的安全回复。用 BLEU 选出的模型，人类满意度往往并不更高。

轮级指标里相对可用的是「上下文感知」的变体：把前一轮的回复也作为条件或参考，衡量回应是否与前文呼应，而不是与某条唯一参考答案比对。即便如此，它仍然无法回答「这轮对推进任务有没有贡献」——这正是必须引入对话级指标的原因。

### Dialogue-Level Metrics

对话级指标衡量整段对话是否达成目的：**任务完成率（task success rate）**、平均轮数、槽位识别准确率（slot accuracy）。这些指标客观、可自动统计，是任务型系统上线看板的主力，但只对「有明确目标」的场景有效，闲聊场景无从定义。

任务完成率通常由模拟用户（user simulator）批量跑出来，好处是可复现、可扩展，代价是模拟用户的分布与真实用户存在差距，出现「指标好而线上差」并不罕见。平均轮数则用来衡量效率：两个系统完成率相同，轮数少的那个体验明显更好。

### User-Level Metrics

用户级指标关注长期体验：满意度评分、问题解决率、留存与复访。它们最贴近产品价值，也最贵、最滞后，通常只能在线上小流量里缓慢采集，且受产品版本、入口位置等混杂因素干扰，很难归因到对话系统本身。

### Human Evaluation and Its Cost

人工评估是这些层次的共同底座，也是最昂贵且最难复现的一环：标注者之间一致性有限、不同研究使用的量表不统一、实验设置差异大，导致跨论文比较几乎不可行。这是对话方向长期效率低下的结构性原因。

此外，人工评估还受指导语影响：同一批对话，要求标注者评「自然度」与评「任务是否完成」，得到的结论可能完全相反。所以严谨的对话研究报告必须同时交代量表、指导语与标注者一致性，而这恰恰是很多论文省略的部分。

### Controllable Attributes

[What makes a good conversation? How controllable attributes affect human judgments](https://arxiv.org/abs/1902.08654) 提供了拆解思路：与其问「整体好不好」，不如把对话质量拆成可控属性——**响应度（responsiveness，是否切题呼应）与信息量（informativeness，是否提供了新信息）**——再分别测量它们对人类判断的影响。这一思路把模糊的整体评分变成了可归因的维度分析：模型可以针对具体属性做调整，评估结果也能指出改进方向，而不只是一个总分。

### LLM-as-Judge

大语言模型出现后，用模型给对话打分（LLM-as-judge）成为常见折中：成本远低于人工、可复现性远好于人工，但存在自身偏好偏差（偏好长回复、偏好与自己风格相似的表达）。当前实践中它更多作为人工评估的粗筛与回归测试工具，而非最终判据。指标设计的通用问题见 [Evaluation](/docs/CS/AI/NLP/Evaluation.md)。

## Dialogue in the LLM Era

[Language Models are Few-Shot Learners-GPT-3](https://arxiv.org/abs/2005.14165) 之后，尤其是对话产品化之后，对话系统的形态被整体重写：模型不再为对话任务专门训练，而是对话成为模型能力的通用接口。几个直接后果：

- **对话即产品**：交互界面即模型本身，系统提示词（system prompt）成为塑造人格、语气与行为边界的核心资产，提示设计从技巧升级为产品资产，产品差异大量体现在提示与约束设计上。

- **记忆与上下文管理成为独立课题**：多轮对话如何压缩、检索、写回长期记忆，机制转入 Agent 与 [RAG](/docs/CS/AI/RAG.md) 讨论。

- **评估重心迁移**：从「这段对话像不像人」转向「任务是否完成 + 是否安全」。任务完成可以用工具调用结果客观判定，安全性则需要专门的对抗测试与人工复核。

最后一条影响最深远：验收方式从「跑一批对话看感觉」变成了更接近传统软件测试的流程——构造任务集、断言工具调用结果、做安全回归。对话系统的工程重心，第一次从「模型调优」转向了「行为约束与验证」。

## Integration Terminal

回到开头：对话系统之所以特殊，不是因为它是某个新任务，而是因为它是**所有 NLP 子任务的集成终端**。理解错了在槽位上暴露，状态维护错了在追问逻辑上暴露，生成不足在话术上暴露，评估缺失则让上面一切无法判定好坏。它把分词的粒度问题、语义的歧义问题、生成的多样性问题、评估的主观性问题全部叠加在一个交互界面里，因此它既是应用形态，也是最诚实的能力试金石。要理解这个子领域的全貌，可从 NLP 的地图出发，沿「任务分解」与「评估瓶颈」两条线展开。
