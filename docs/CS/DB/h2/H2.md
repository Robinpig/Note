## Introduction

H2 是**纯 Java 编写的开源 SQL 关系型数据库**，官方自我定位就是「the Java SQL database」：极快的引擎、标准 SQL 与 JDBC API、嵌入式与服务端双模式、内存库、浏览器 Console、**约 2.5 MB 的 jar 体积**（Maven Central 上 `com.h2database:h2` 当前 release 为 **2.5.252**，jar 实测 2,693,360 字节）。双许可：**MPL 2.0 或 EPL 1.0**。

它是嵌入式 Java RDBMS 这一格里功能面最宽的一个：SQLite 是 C 库、Derby 与 HSQLDB 偏保守，H2 同时把「进程内零运维」和「一台机器上跑个小服务端」两件事做进了同一个 jar，还额外提供一层 PostgreSQL 协议兼容，让 PG 的 ODBC 驱动能直接连上来。

> [!WARNING]
> **本套笔记的版本锚点是 2.5.252，且刻意以源码为准而不是以手册为准。** 这不是修辞：核实过程中发现官方文档在多处已经落后于代码——MVStore 在文档里**没有专门章节**（`h2database.com/javadoc/org/h2/mvstore/package-summary.html` 直接 404），`SET LOCK_TIMEOUT` 的默认值文档写 1000 ms 而源码常量是 2000 ms，「最多 65535 个活动事务」源码默认是 255，`CACHE_TYPE=TQ` / `SOFT_LRU` 这些文档还在介绍的缓存实现**已经是没有调用方的死代码**（实际永远走 LIRS）。每处冲突在下文都同时给出两边并注明以哪边为准。

## Three Orthogonal Dimensions

理解 H2 要先拆开三个互相正交的维度，很多描述（包括本页旧版）把它们揉成了「三种模式」：

| 维度 | 取值 | 由什么决定 |
| :--- | :--- | :--- |
| 连接模式 | Embedded / Server / Auto-Mixed | JDBC URL 前缀（`file:`、`tcp://`、`ssl://`、`mem:`）与 `AUTO_SERVER` |
| 数据存放 | 持久化文件 / 纯内存 | URL 是 `mem:` 还是文件路径 |
| 协议入口 | JDBC、TCP/IP、TLS over TCP、PostgreSQL 协议（可用 PG 的 ODBC 驱动） | 启动哪种 server |

**「In-Memory」不是与 Embedded 并列的第三种运行模式**：嵌入式完全可以持久化，服务端也可以服务内存库（`jdbc:h2:tcp://localhost/mem:test`）。展开见 [Connection_and_Servers](/docs/CS/DB/h2/Connection_and_Servers.md)。

## Architecture

```
JDBC / TCP(9092) / TLS / PG 协议(5435) / Web Console(8082)
        │
   SessionLocal ── 事务：内存 undo(radix tree) + MVStore 键级锁
        │              └── 5 档隔离级别，默认 READ_COMMITTED
   Table / Index（MVPrimaryIndex / MVSecondaryIndex）
        │              └── 每张表/索引 = MVStore 里的一个 map：table.<id> / index.<id>
      MVStore ── copy-on-write B-tree + 日志结构 chunk（`.mv.db` 就是它）
        │
   FileStore ── FileEncrypt(AES-XTS) ── 本地文件 / nioMapped: / zip:
```

四个层次各自都可以单独配置，这正是 H2 与「只是个单文件库」印象的差别所在：

- **协议与会话层**：三种 server 形态 + 内嵌，跨进程共享靠 `.lock.db` 与 `AUTO_SERVER`。见 [Connection_and_Servers](/docs/CS/DB/h2/Connection_and_Servers.md)。
- **事务与并发层**：MVCC + 键级锁 + 真实的死锁检测（等待图，选最年轻事务当 victim），以及一个不显眼但很关键的 `retentionTime`（默认 45 s）决定旧版本还能被读多久。见 [Transactions_and_Locks](/docs/CS/DB/h2/Transactions_and_Locks.md)。
- **SQL 层**：完整的 `GENERATED ... AS IDENTITY`、窗口函数、`QUALIFY`、`ENUM`/`JSON`/`GEOMETRY`/`ROW` 类型，以及一批**只在特定兼容模式下才存在**的语法（`ON CONFLICT` 属于 PostgreSQL 模式、`ON DUPLICATE KEY UPDATE` 属于 MySQL/MariaDB 模式）。见 [SQL_Language](/docs/CS/DB/h2/SQL_Language.md) 与 [Compatibility_Modes](/docs/CS/DB/h2/Compatibility_Modes.md)。
- **存储层 MVStore**：一个可以脱离 SQL 单独使用的多版本 KV，chunk 追加 + 空闲空间复用 + 后台写。见 [MVStore](/docs/CS/DB/h2/MVStore.md)。

## Facts Worth Pinning Down

这几条要么反直觉、要么被大量资料写错，放在最显眼处：

- **默认文件锁协议是 `FS`（`FileChannel.lock`），不是文档写的 `FILE`**；只有 `AUTO_SERVER=TRUE` 时才强制回落到 `FILE`（watchdog 每 1000 ms 复查锁文件）。`Database.java:246-248`。
- **新库页大小：文档 `features.html` 说 4 KiB、`Limits` 一节说 2 KiB，源码 `Constants.DEFAULT_PAGE_SIZE` 是 16 KiB**，而且它在 MVStore 里的实际角色是「页分裂阈值」而非固定页大小。加密库要求页大小是 4096 的倍数这点属实。
- **`.mv.db` 主文件的加密与 URL 里的 `CIPHER` 名字无关**：永远走 `FileEncrypt` = PBKDF2(SHA-256, 10 轮) 派生 16 字节密钥的 **AES-128-XTS**；`CIPHER=XTEA/FOG` 真正生效的范围是 LOB/临时文件与脚本文件。
- **并发打开的事务数：源码默认 255**（`h2.maxOpenTransactions`，且它是 JVM 全局静态量，按库设置无效），文档 `Limits and Limitations` 写的 65535 是历史值。
- **没有 `INSERT/UPDATE/DELETE ... RETURNING`**：要拿回生成的键值，用数据变更增量表 `SELECT ... FROM FINAL TABLE (INSERT ...)` 或 JDBC `getGeneratedKeys()`。
- **`GROUP_CONCAT` 只是 `LISTAGG` 的解析别名**；压缩函数叫 `COMPRESS` / **`EXPAND`**（不是 `DECOMPRESS`，也没有 `COMPRESS_X/Z`）。
- 递归 CTE 官方标注 **experimental**；`PIVOT/UNPIVOT`、`GROUPING SETS/CUBE/ROLLUP`、`CREATE TABLE LIKE`、`DELETE ... USING`、`COPY` 语句在 H2 中**不存在**。

## Durability: 官方自己承认的边界

H2 文档在这一点上异常坦诚，值得原样转述：**「声称能保证持久性的数据库都是错的」**。官方自带一个掉电测试（`org.h2.test.poweroff.Test`）跑过 H2、HSQLDB、PostgreSQL 与 Derby，结论是**它们都可能丢已提交事务**——差异只在 `rws` / `rwd` 同步写与磁盘自身写缓存的组合方式。落到使用上：`WriteOptions`-级别的安全感来自 WAL/日志顺序写，而不是「提交返回 = 已在物理介质上」。

## Limits and Known Boundaries

| 项 | 上限 | 备注 |
| :--- | :--- | :--- |
| CHAR / VARCHAR | 1,000,000,000 字符 | `CHARACTERS` / `OCTETS` 单位在 H2 无效 |
| BINARY / BINARY VARYING / JAVA_OBJECT / GEOMETRY / JSON | 1,000,000,000 字节 | 更大内容用 `CLOB` / `BLOB` 大对象类型 |
| NUMERIC / DECIMAL 精度 | 1–100000 | **无参时 scale=0**（1.x→2.x 行为反转） |
| TIMESTAMP 分数秒 | 0–9，默认 6 | TIME 默认 0 |
| INTERVAL 前导精度 | 1–18，默认 2 | 秒分数 0–9，默认 6 |
| ENUM | 最多 65536 个值，**序数 1-based** | 1.x 是 0-based |
| ARRAY | 基数 0–65536，**元素强类型** | 混合类型不支持（改用 `ROW`） |
| 标识符长度 | 256 字符 | |
| 同时打开的事务 | **255（源码默认）** | 文档写 65535 |
| MVStore 页最大 | 2 MiB（编码位限制，超出走 LARGE 页） | |

结构上的边界更值得记住：

- **单写进程模型**：一个库同一时刻只属于一个 JVM（跨进程共享必须走 server 模式或 `AUTO_SERVER`）。
- **没有真正的集群**：所谓 Clustering 是「两台机器各存一份、双写、单侧挂了另一侧继续」的简单 HA，只能配 server 模式使用，且不提供仲裁——**脑裂时可能双写**，重建靠 `CreateCluster` 工具。
- **空间不会自动归还**：`DROP TABLE` 的 map 删除是**延迟**的，页回收要等 `autoCompactFillRate`（默认 90%）触发；关闭时默认只压缩 200 ms，要真正缩库得 `SHUTDOWN COMPACT`，或 `SCRIPT` 导出 + `RUNSCRIPT` 重建（顺带重建索引）——这两个命令的完整选项与 12 个命令行工具的分工见 [Tools_and_Operations](/docs/CS/DB/h2/Tools_and_Operations.md)。
- **`MAX_MEMORY_UNDO` 是死参数**：语法保留、源码里没有任何消费方。同类还有 `CACHE_TYPE`。

## Applicable Scenarios

适合：单元/集成测试与本地开发（`jdbc:h2:mem:` + `INIT=RUNSCRIPT` 建表，秒级起停）、桌面与边缘设备的内嵌存储、打包成 zip 的只读数据集（`jdbc:h2:zip:~/data.zip!/test`）、小型内部系统直接起 TCP/TLS server 或 PG 协议端点、用 `MODE=` 在 CI 里贴近目标方言、以及把 MVStore 单独当持久化 `Map` 用。

不适合：多写高并发、需要水平扩展或多副本强一致的场景、把 PG 协议端点当安全通道（不支持 SSL、口令明文传输、语句无法取消）、以及依赖「兼容模式 = 目标数据库」这件事——官方明确说每种模式**只实现了差异的一小部分**。详见 [Compatibility_Modes](/docs/CS/DB/h2/Compatibility_Modes.md)。
