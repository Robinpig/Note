## Introduction

H2 是**纯 Java 编写的开源 SQL 关系型数据库**，官方自我定位就是「the Java SQL database」：极快的引擎、标准 SQL 与 JDBC API、嵌入式与服务端双模式、内存库、浏览器 Console、**约 2.5 MB 的 jar 体积**（Maven Central 上 `com.h2database:h2` 当前 release 为 2.5.252，jar 实测 2,693,360 字节）。双许可：**MPL 2.0 或 EPL 1.0**，可自由选择。

它是嵌入式 Java RDBMS 这一格里功能面最宽的一个：SQLite 是 C 库、Derby 与 HSQLDB 偏保守，H2 同时把「进程内零运维」和「一台机器上跑个小服务端」两件事都做进了同一个 jar。

理解 H2 要先拆开三个**互相正交**的维度，很多描述（包括本页旧版）把它们揉成了「三种模式」：

| 维度 | 取值 | 由什么决定 |
| :--- | :--- | :--- |
| 连接模式 | Embedded / Server / Auto-Mixed | JDBC URL 前缀（`file:`、`tcp://`、`ssl://`、`mem:`）与 `AUTO_SERVER` |
| 数据存放 | 持久化文件 / 纯内存 | URL 是 `mem:` 还是文件路径 |
| 协议入口 | JDBC、TCP/IP、TLS over TCP、PostgreSQL 协议（可用 PG 的 ODBC 驱动） | 启动哪种 server |

嵌入式完全可以持久化，服务端也可以服务内存库（`jdbc:h2:tcp://localhost/mem:test`），「In-Memory」不是与 Embedded 并列的第三种运行模式。

## Connection Modes

- **Embedded（本地 JDBC）**：应用在自己的 JVM 里直接打开数据库，**最快、最省事**。代价是一条硬约束：**同一个库同一时刻只能被一个虚拟机（且一个 class loader）打开**，第二个进程会被 `.lock.db` 挡在外面。除此以外没有并发限制——同时打开的库数、连接数都不设上限。另外要注意 I/O 是由**执行 SQL 的应用线程**直接做的，应用的线程模型会直接反映成数据库的 I/O 行为。
- **Server（远程）**：一个进程当 server，其它进程（可在别的机器）走 TCP/IP 连入；需要加密链路时用 `ssl://`（TLS，基于 JSSE 的 `SSLServerSocket`，自定义 keystore 用 `javax.net.ssl.keyStore` 系列系统属性）。ODBC 亦可经 TCP 使用，并且 H2 提供 PostgreSQL 协议兼容，能直接套 PG 的 ODBC 驱动。
- **Auto-Mixed（`AUTO_SERVER=TRUE`）**：多进程共享同一个库又不想手工起 server 时的折中——第一个连接以 embedded 打开并在内部起一个 daemon 线程 server，后来的进程自动转成 client/server；server 的地址与端口就记在 `.lock.db` 里。**该特性对内存库无效**，且所有连接必须使用同一个 URL。

URL 上最常用的几个开关：

| 片段 | 作用 |
| :--- | :--- |
| `jdbc:h2:mem:` / `jdbc:h2:mem:db1` | 私有内存库 / 具名内存库（具名才能被同 JVM 多连接共享；两个 `mem:` 连接不具名 = 两个不同库） |
| `;IFEXISTS=TRUE` | 库不存在就直接报错，避免打错路径顺手建了个空库 |
| `;DB_CLOSE_ON_EXIT=FALSE` | 阻止 VM 退出时自动关库（嵌入式 + 连接池场景常见） |
| `;INIT=RUNSCRIPT FROM '~/create.sql'` | 每次连接执行 SQL；多条语句用 `\;` 分隔 |
| `;CIPHER=AES` | 文件加密，密码分文件密码与用户密码两段输入 |
| `;FILE_LOCK={FILE|SOCKET|FS|NO}` | 锁文件协议，选择依据见下文 MVStore 一节末尾 |
| `;PAGE_SIZE=512` | 只在**建库时**有效，已有库不可改 |

## Storage Engine: MVStore

2.x 的默认存储层是 **MVStore**（multi-version store），1.x 时代的 PageStore 已退出默认路径（官方文档为它单列了 *Migration to 2.0*）。它的本质是**日志结构（log-structured）的多版本 KV 存储**，上面跑 copy-on-write 的 B-tree。官方对它的类比相当直白：**工作方式类似 Btrfs**。

结构要点：

- 数据按 **chunk** 追加写入；没有存活页的 chunk 被标为 free，空间由更新的 chunk 复用。因为 chunk 大小不一，chunk 前面可能残留一段空闲块，要靠 defrag 才能收回。
- 与传统引擎的「事务日志 + undo log + 主数据区」三段式相比，日志结构的每次变更**只写一次而不是两三次**，大 key 与大页不需要特殊分支；BLOB 通过拆成小块存放。
- 除了作为 H2 的存储层，MVStore **可以绕开 JDBC/SQL 直接在应用里当 `java.util.Map` 用**（`MVMap`、`MVStore.Builder` 流式配置，支持文件持久化与纯内存）——这一点常被忽略，它本身就是一个嵌入式持久化 Map。
- 常用配置：`cacheSize`（MB）、`compress`（LZF 快速压缩）、`compressHigh`（Deflate）、`encryptionKey`（文件加密）、`backgroundExceptionHandler`（后台写异常处理）。

**一个持久化库会产生的文件**：

| 文件 | 内容 | 数量 |
| :--- | :--- | :--- |
| `test.mv.db` | 主数据文件：事务日志、索引与全部表数据 | 每库 1 |
| `test.lock.db` | 锁文件，库被使用时自动创建/删除，内含连接信息 | 使用中 1 |
| `test.trace.db` | trace 日志，过大时轮转为 `.trace.db.old` | 0 或 1 |
| `test.newFile` / `test.tempFile` | compaction 期间的临时文件 | 0 或 1 |
| `test.<n>.temp.db` | 临时 BLOB 或大结果集 | 按需 |

**页与缓存**：新建库页大小 4 KiB（`PAGE_SIZE=` 建库时可改，之后不可改；加密库页大小必须是 4096 的倍数）。`CACHE_SIZE` 单位是 KB（1024 字节），持久库会把该设置存进库并在下次打开时复用，但打开时会被压到**不超过 JVM `maxMemory()` 的一半**；内存库不受该设置影响。

**崩溃恢复**：提交时先写事务日志，主数据区的落盘通常延后进行；掉电后下次打开会自动重放日志。关闭数据库时默认最多花 200 ms 做 compaction，想多压缩用 `SHUTDOWN COMPACT`；要真正把库缩小还得重建（`SCRIPT` 导出 + `RUNSCRIPT` 导入，顺带重建索引）。

**只读与锁协议**：把 `.mv.db` 设成文件系统只读，库即为只读（只允许 `SELECT` 与 `CALL`，可用 `CALL READONLY()` 或 `Connection.isReadOnly()` 判断；也可用自定义访问模式 `r` 在文件可写时强开只读）。只读库甚至可以直接打包在 zip / jar 里访问。锁文件协议三选一：`FILE`（默认，watchdog 线程每秒读一次锁文件）、`SOCKET`（开一个 server socket，不轮询，但**只应在文件仅由同一台机器访问时使用**）、`FS`（`FileChannel.lock` 原生锁）——容器/NFS 场景选错会表现为「库明明没人用却打不开」。

## Transactions and Concurrency

- **隔离级别**：默认 **read committed**；另支持 read uncommitted、repeatable read、**snapshot**，以及**部分** serializable。注意大多数 DDL（如 `CREATE TABLE`）会**提交当前事务**。
- **MVCC 的锁形状**：insert/update 只加**表级共享锁**，只有增删列、drop table 才升级为排他锁。连接只看到已提交数据与自己的改动（即 read committed 语义）；多个连接争同一行时数据库会等待，直到能执行或**锁超时**。
- **锁超时可调**：`SET LOCK_TIMEOUT <ms>` 对当前连接生效，`SET DEFAULT_LOCK_TIMEOUT <ms>` 改新连接的初值。「写入莫名卡住几十秒后报 lock timeout」是默认超时在起作用，不是数据库死了。
- **两阶段提交（2PC）**：关掉 autocommit → 操作 → `PREPARE COMMIT <transactionName>` → 提交或回滚；期间出问题（如网络故障）事务进入 **in-doubt**，重连后可从 information schema 里查出来处理。
- **线程模型**：数据库本身多线程安全，应用无需自己加锁；官方建议**一个连接一个线程**（同一连接上的访问由数据库串行化）。
- **持久性的诚实边界**：官方直接写了「声称能保证持久性的数据库都是错的」，并给出自己跑的掉电测试（`org.h2.test.poweroff.Test`，对比 HSQLDB、PostgreSQL、Derby，结论是**它们都可能丢已提交事务**）。差异在于 `rws` / `rwd` 同步写与磁盘自带写缓存的组合——把「已提交即不丢」当成物理保证是误用。

## SQL Feature Set

H2 的功能面在嵌入式阵营里明显偏大，官方特性清单里值得单拎出来的：

- **查询能力**：窗口函数；`OFFSET/FETCH`（含 `PERCENT`、`WITH TIES`）与 `LIMIT`/`TOP`；`DISTINCT ON (...)`；内外连接、子查询、只读视图与内联视图，另有可更新视图；collation 支持，且可挂 **ICU4J**。
- **递归查询**：`WITH RECURSIVE` 通用表表达式可用，但官方标注为**实验性**。
- **对象与约束**：多 schema + `information_schema`；带级联的外键、check 约束；sequence 与 identity 列；用户与角色；`CREATE MATERIALIZED VIEW` / `REFRESH MATERIALIZED VIEW`。
- **类型**：宽类型族，含 BLOB/CLOB、数组、`UUID`、`ENUM`、`JSON`，以及 `GEOMETRY`（见下）。
- **生成列（generated column）**：值在写入与更新时计算、不可直接赋值。两个高频用法——自动维护 `LAST_MOD`，以及**用生成列模拟函数索引**（H2 不直接支持 function-based index，把 `UPPER(x)` 存成生成列再建 [Index](/docs/CS/DB/Index.md) 即可）。
- **Java 扩展三件套**：
  - `CREATE ALIAS` 注册 **Java 函数**，也能当存储过程用（只支持 `public static` 方法；可用源码即时编译，也可引用 classpath 上已编译的类）。
  - **Java 触发器**：实现 `org.h2.api.Trigger`，在行 insert/update/delete 前后回调；server 模式下类必须在**服务端** classpath。
  - **Pluggable tables**：实现 `org.h2.api.TableEngine` 把任意外部数据源暴露成表（`CREATE TABLE ... ENGINE "acme.MyTableEngine"`，可带参数）。
- **联邦查询**：`CREATE LINKED TABLE` 建立指向另一个数据库的链接表，访问时把条件**下推**成远程 SQL（例：`SELECT * FROM LINK WHERE ID=1` 会在远端执行 `SELECT * FROM TEST WHERE ID=1`），配 `org.postgresql.Driver` 之类的远程驱动即可跨库查。
- **空间与多维**：`GEOMETRY` 列 + `CREATE SPATIAL INDEX`，查询用 PostGIS 风格的 `&&`（envelope 相交）。而**通用多维范围查询**上，H2 没有 R-Tree，走的是把多维坐标 **bit-interleaving 折叠成 Z-order（Morton order）标量**、再交给普通 B-Tree 索引的路子（通常配一个生成列承载该标量）——官方称相比只用普通索引硬扫有明显改善，Hilbert 曲线理论上也可行，只是实现更复杂。
- **优化器**：基于代价（cost-based），复杂查询用**遗传算法**搜索连接顺序。
- **LOB 与结果集**：可滚动可更新结果集、外部排序大结果集、函数可返回结果集；client/server 模式下大 BLOB/CLOB 会**在客户端**落临时文件。

## Compatibility Modes

H2 可以按目标库调整行为，但官方限定得很清楚：**只实现了差异中很小的一部分**。

| 模式 | 用途 |
| :--- | :--- |
| `REGULAR` | 默认。允许一批非标准便利行为：空 `IN` 谓词、`TOP`、`OFFSET/LIMIT`、用 `MINUS` 代替 `EXCEPT`、`IDENTITY` 当数据类型、`SERIAL`/`BIGSERIAL`、`AUTO_INCREMENT` |
| `LEGACY` | 为 H2 1.x 时代写的应用重新打开上述兼容特性；**不等于完整 1.x 兼容** |
| `STRICT` | 关掉部分弃用特性。官方建议**在单元测试里用它**，以免应用或库代码悄悄依赖了这些宽松行为 |
| 目标库仿真 | IBM DB2、Apache Derby、HSQLDB、MS SQL Server、MySQL、Oracle、PostgreSQL |

模式写在 URL（`;MODE=MySQL;DATABASE_TO_LOWER=TRUE`）或运行时 `SET MODE ...`。这套机制的真正价值是**在 CI 里用 `mem:` 跑贴近生产的方言**，而不是把 H2 当 MySQL 的替代品——仿真覆盖的是语法习惯，不是语义与并发行为。Spring Boot 的 `@DataJpaTest` 默认就把数据源换成内存 H2，于是「厂商特有 SQL 在测试里全绿、上生产才炸」，破解办法见 [Spring Boot Test](/docs/CS/Framework/Spring_Boot/Test.md)。

## Tools and Operations

- **Web Console**：浏览器里的 SQL 客户端与库管理界面，H2 最广为人知的入口。
- **Recover 工具**（`java -cp h2*.jar org.h2.tools.Recover`）：即使库文件损坏也能把内容导出成文本 dump（`*.mv.txt`）与 SQL 脚本（`*.h2.sql`），事务日志与 LOB 一并抽出；导出文件未压缩，约占数据库两倍的盘。
- **备份**：`BACKUP TO '...'`、`SCRIPT`（导 DDL + 数据）、`RUNSCRIPT`（导入）；库关闭后直接复制 `.mv.db` 也是可行的文件级备份。
- **远程访问默认关闭**：起 Console / TCP server / PG server 时**默认不接受其它机器连接**，要放开必须显式给 `-webAllowOthers` / `-tcpAllowOthers` / `-pgAllowOthers`；官方同时要求配合 `-baseDir` 限定可访问目录，否则远程用户能自建库、或用弱口令访问已有库。也就是说：暴露面一旦被打开而目录与口令没管住，嵌入式数据库立刻变成公网入口——这是 H2 部署最常见的误配。
- **观测**：trace 选项控制 `*.trace.db` 的详细度；`EXPLAIN` 与 `ANALYZE` 看计划与统计。

## Limits and Trade-offs

官方的 *Limits and Limitations* 给出的硬边界（比「嵌入式 = 无所不能」的想象要早撞墙）：

| 项 | 上限 |
| :--- | :--- |
| 数据库文件大小 | 4 TB（含 CLOB/BLOB；用更大页可更高。该节文字仍写「默认页 2 KB」，与 Features 一节的新库 4 KiB 自相矛盾，以 4 KiB 为准） |
| FAT / FAT32 文件系统 | 实际受限于 4 GB；H2 提供 `jdbc:h2:split:~/test` 前缀，按默认 1 GB 切片绕过 |
| 单表行数 | 2^64 |
| 同时打开的事务数 | 65535 |
| 表的列数 / SELECT 表达式数 | 16384 |
| 标识符长度 | 256 字符 |
| VARCHAR 值长度 | 1,000,000,000 字符 |
| BINARY / JAVA_OBJECT / GEOMETRY / JSON | 1,000,000,000 字节 |
| NUMERIC / DECFLOAT 精度 | 100000 |
| ENUM | 单值最长 1,048,576 字符，最多 65536 个值 |
| ARRAY 基数 / ROW 度 | 65536 / 16384 |

结构上的取舍：

- **没有分布式**。所谓 *Clustering / High Availability* 是「两台机器各存一份、正常时双写、其中一台挂了另一台继续跑」的简单机制，**且只能用在 server 模式**（embedded 不支持集群）；集群可用 `CreateCluster` 工具在不中断存活端的前提下重建，配合 `AUTO_RECONNECT=TRUE` 让客户端自动接回。
- **单写进程模型**：embedded 下一库一 JVM，横向扩展不是 H2 的目标；真要多副本一致读写，那是 [PostgreSQL](/docs/CS/DB/PostgreSQL/PostgreSQL.md)、[MySQL](/docs/CS/DB/MySQL/MySQL.md) 或分布式的活。
- 与同为嵌入式 RDBMS 的 SQLite（C 实现、零依赖、生态最广）、Derby（纯 Java、JDK 时代遗留）、HSQLDB（纯 Java 老将）相比，H2 的差异点是**性能、Java 侧可扩展性（UDF/触发器/TableEngine）、浏览器 Console、以及协议与服务端形态的丰富度**。

## Applicable Scenarios

适合：单元/集成测试与本地开发（`jdbc:h2:mem:` + `INIT=RUNSCRIPT` 建表，秒级起停）、桌面与边缘设备的内嵌存储、打包成 zip/jar 的只读数据集、小型内部系统直接跑个 TCP/TLS server、用 `MODE=` 在 CI 里贴近目标方言、以及把 MVStore 单独当持久化 `Map` 用。

不适合：高并发多写、超大数据集、需要水平扩展或多副本一致性的场景；以及把 `AUTO_SERVER` 当集群、把仿真模式当生产等价物这两种典型误用。
