## Introduction

推荐系统里模型代码只占一小部分工作量，剩下的大头在数据：**埋点口径、日志正确性、特征一致性、样本构造与监控**。原因很直接——模型的输入是样本，而样本是这几层加工后的产物；任何一层口径错，模型都会"忠实地学错东西"，并且从指标上看不出来。

这一篇沿着数据流从上到下走一遍：行为事件 → 日志 → 明细分层 → 特征 → 样本 → 训练/打分，并标出每一段的典型事故形态。链路的业务侧顺序见 [Pipeline](/docs/CS/RecommenderSystem/Pipeline.md)，在线读取与部署侧见 [Architecture](/docs/CS/RecommenderSystem/Architecture.md)。

## Event Tracking and Event Model

埋点决定了系统"能知道什么"。三类事件缺一不可：

| 事件 | 作用 | 最常见问题 |
| ------ | ------ | ------ |
| 请求/下发 | 记录候选集合与位置，是反事实评估的唯一来源 | 只记了最终曝光，未曝光候选无从追溯 |
| 曝光 | 负样本的来源 | "下发即曝光"导致分母虚高，CTR 被系统性低估 |
| 行为 | 正样本与反馈信号 | 只埋点击，漏掉完播/跳过/负反馈这类更强的信号 |

几条实践口径：

- **曝光不等于下发**：真实曝光至少要满足"进入可视区域 + 面积占比 + 停留时长"的阈值，阈值本身要可配置并写进口径文档。用下发当曝光，等于把用户没看见的东西当成他拒绝了的
- **主键三元组**：`user_id + item_id + request_id`，再加位置 `position`、模块/页面、时间戳（事件时间与服务端接收时间都要留）。缺 `request_id` 就无法把候选集与结果对齐，反事实与去偏全部做不了（见 [Debiasing](/docs/CS/RecommenderSystem/Debiasing.md)）
- **上下文字段要在事件里，而不是事后关联**：网络、机型、地理位置、会话状态这类字段事后补不回来
- **改语义比加字段危险得多**：给事件加字段是兼容变更，改字段含义是不兼容变更。正确做法是新字段双写、口径版本号推进、老字段留观察期，而不是原地改
- **客户端时钟不可信**：改系统时间就能伪造时间戳，跨端拼接时要以服务端接收时间做仲裁，并监控事件时间与接收时间的差值分布

## Log Transport and Tiering

从端上到可查询，路径通常是：采集网关（校验、限流、黑名单）→ 消息队列（见 [Kafka](/docs/CS/MQ/Kafka/Kafka.md)）→ 流式处理（见 [Flink](/docs/CS/Framework/Flink/Flink.md)）→ 明细存储 → 汇总与应用层表。

数仓分层用广泛采用的叫法：**ODS**（原始明细，贴近日志结构）→ **DWD**（清洗后事实明细，统一口径与维度）→ **DWS**（按主题聚合，如用户日粒度行为汇总）→ **ADS**（面向应用的结果表，含样本表与特征表）。分层的意义不是仪式感，而是**让"口径"只在一个地方定义一次**。

流处理侧必须显式处理三件事：

- **乱序**：移动端网络导致事件到达顺序与发生顺序不一致。用语件事件时间 + 水位线（watermark）容忍迟到，超过容忍度的迟到数据走旁路补算，而不是假装不存在
- **重复**：至少一次投递必然带来重复，因此所有写入都要有幂等键，统计口径要按主键去重而不是按行数
- **丢失与延迟**：区分"没采到"与"还没到"。二者的处理完全不同——前者要修链路，后者要等或补。监控上分别对应采集成功率与端到端延迟分位数

Lambda（离线全量 + 实时增量双链路）与 Kappa（纯流重放）的取舍在于：实时链路的口径能否与离线严格等价。实践中最常见的坑不是选错架构，而是**两条链路各写了一套统计逻辑**，于是实时看板和离线报表长期不一致。

## Data Side of Feature Engineering

特征一致性有三个层次，越往下越难查：

- **定义一致**：同一个特征名在离线 SQL 与在线代码里必须是同一套计算。解法是特征定义集中化（注册表或统一算子/DSL），两端生成而不是两端手写
- **时间一致**：训练时特征取"曝光那一刻"的值。用当前值重算历史特征叫**特征穿越**，它让离线指标漂亮到不可信。工程上的防线是 point-in-time 拼接（按事件时间做"截止该时刻"的关联，类似 `AS OF JOIN` 语义），以及禁止特征表里出现"含未来窗口"的统计列
- **分布一致**：同一个特征在离线与在线的取值分布应当吻合。做法是**对拍**——上线前把线上真实请求旁路送去离线计算，比较两边特征与打分的差异，接受阈值要事先定而不是事后解释

特征监控的四项基本盘：覆盖率（有多少请求带这个特征）、缺失率与其变化、分布漂移（PSI，定义见 [Evaluation](/docs/CS/RecommenderSystem/Evaluation.md)）、新鲜度（值的时间戳距当前多久）。**缺失率突增往往是上游表变更，而不是用户行为变了**——先查血缘，再查口径。

## Sample Construction

样本表是整个数据链路的出口，也是训练效果的第一道闸门：

- **一行一个决策点**：以"（请求，候选，位置）"为主键，把下发、曝光、行为按同一时间口径关联起来。保留未曝光候选是做去偏与离线重放的必要条件
- **标签窗口与成熟期**：点击几秒内成熟，加购分钟级，转化天级，留存以周计。窗口未关闭就落表，会把"还没来得及转化"错当成负样本。常见处理是"未成熟样本先按概率计入、到期后再修正"，或者把标签窗口拆成多列分别使用
- **降采样要留下还原入口**：负样本下采样能提速，但模型输出就不再是真实概率，必须同时记录采样率以便在线校准还原（公式见 [Ranking](/docs/CS/RecommenderSystem/Ranking.md)）
- **过滤顺序**：反作弊/爬虫 → 无效设备与自点击 → 重复上报 → 客户端缓存重放。顺序影响结论，必须先于统计固化并写进文档
- **可回溯**：样本表要能回答"这条样本为什么在这里"。缺可回溯性时，一次数据事故的损失不是几天模型，而是几周无法解释的指标漂移

## Public Datasets and Reproduction Pitfalls

做算法验证绕不开公开数据，但它的适用边界必须先看清：

| 数据集 | 形态 | 适合什么 | 不适合什么 |
| ------ | ------ | ------ | ------ |
| MovieLens（[GroupLens](https://grouplens.org/datasets/movielens/)） | 显式评分 0.5–5 星，带时间戳与电影元数据，规模从十万到千万级评分 | 评分预测、矩阵分解与序列模型的可复现对比 | 现代隐式反馈链路；没有真实曝光机制与位置信息 |
| 电商评论/交易类（如 Amazon Reviews 系） | 购买与评论行为 + 商品文本 | 内容画像、跨品类迁移、冷启动实验 | 缺曝光候选集；类目分布极度不均 |
| KuaiRand（[arXiv:2208.08696](https://arxiv.org/abs/2208.08696)） | 短视频隐式反馈，**含随机曝光子集** | 有偏/无偏对比、去偏算法与离线评估的可信标尺 | 单平台单场景，结论外推要小心 |

四个反复出现的复现陷阱：

- **按行随机划分**：同一用户同时出现在训练与测试里，等于把答案泄漏给模型。必须按时间切分（并按用户分组做置信区间）
- **候选集未限定**：全库排序时把"用户确实想看的历史物品"当正例，等于奖励"预测他会回看"，与真实系统的曝光过滤逻辑相反
- **缺曝光机制**：没有下发与位置信息，就无法评估去偏效果——任何声称"消除了位置偏差"的结论在这种数据上无法检验
- **流行度天然存在**：真实行为是幂律分布，随机负采样会人为夸大指标；负采样协议必须在报告里写清，否则同一数据集上不同论文的分数不可比

在公开数据集上的提升与线上收益之间，通常隔着一整条"真实反馈回路"。合理用法是：**公开数据做方法可行性与可复现性，业务数据做离线验证，随机流量做无偏评估，A/B 实验做决策**（见 [Evaluation](/docs/CS/RecommenderSystem/Evaluation.md)）。
