## Introduction

直播是一条很长的链路：**采集 → 前处理（美颜、降噪）→ 编码 → 推流到源站 → CDN 分发 → 边缘拉流 → 解码 → 渲染**。每一段都贡献时延，也都可能各自成为卡顿的来源。所以直播优化不是单点调优，而是先定下 QoE 目标（秒开率、卡顿率、端到端时延），再倒推每个环节的预算——做法与 [Performance](/docs/CS/SE/Performance.md) 一致：先度量，再针对瓶颈改。

这条链路与点播最大的差别在于**实时性与可预测性的取舍**：点播可以靠预缓冲换取流畅，直播必须在"时延尽可能小"和"缓冲足够吸收网络抖动"之间找平衡，而这个平衡点会随场景漂移——秀场直播容忍几秒时延，连麦互动则不能。

## Stream Metrics

- 帧率 fps
- 分辨率
- 时延
- 流

此外还有两个直接决定用户感受、但常被忽略的指标：**首帧时间（秒开）**与**卡顿率**（单位时间内的卡顿次数/时长）。

## Streaming Protocols

- RTSP
- RTMP
- HLS

三者之外，实践中还会遇到 HTTP-FLV 与 WebRTC，按各自的取舍选择：

| 协议 | 特点 | 常见位置 |
|------|------|---------|
| RTSP | 早期的流媒体会话控制协议，本身不承担数据传输 | 摄像头、监控、局域网设备 |
| RTMP | 基于 TCP 的长连接推流协议，时延低、生态成熟 | **推流侧的事实标准** |
| HTTP-FLV | 用 HTTP 长连接承载 FLV 分片，穿透性好、时延较低 | 低时延拉流 |
| HLS | 切片（TS / fMP4）+ m3u8 索引，纯 HTTP，穿透性与适配性最好，**时延随切片时长放大** | 移动端拉流、跨平台场景 |
| WebRTC | 以 UDP 为主，亚秒级时延，可双向实时互动 | 连麦、低延迟互动（服务端复杂度与成本最高） |

推流 尽量 RTMP

移动端尽量 HLS

这条默认的背后是环境的现实：RTMP 在推流侧被 CDN 普遍支持且实现成熟；而移动端拉流用 HLS，是因为它基于标准 HTTP、能穿透大部分网络限制与防火墙策略，且系统播放器原生支持，兼容性风险最小。时延敏感的场景才在此基础上换成 HTTP-FLV 或 WebRTC。

## Live Messaging

直播消息 使用 [IM](/docs/CS/SE/IM/IM.md)（弹幕、点赞、礼物、进场提示都属于 IM 能力而非流媒体能力），它的难点不是收发本身，而是**高并发下的扇出与降频**——万人房间的消息风暴要靠合并下发、分级丢弃来控制，否则会把客户端和服务端一起拖垮。消息到达端的保活问题见 [Client](/docs/CS/SE/IM/Client.md)。

## Ordering and Versioning

进入/离开直播间需要加上版本控制 防止网络等原因导致请求乱序造成非预期后果
由端上生成时间戳送往服务器

这条在手滑进出直播间、弱网重连的场景下尤其关键：网络重排会让"先进房后出房"变成相反的到达顺序，服务端若按到达顺序处理，用户状态就与实际不符。加上由端侧生成的时间戳/版本号后，服务端可以据此丢弃过期请求。它与 [掉单机制](/docs/CS/SE/掉单机制.md) 里的幂等处理是同一类思路——**承认消息会乱序、会重复，把正确性建立在幂等而非理想网络上**。

## Where Optimization Usually Happens

- **秒开**：GOP 缓存（不必等一个完整 GOP 才开始播）、就近调度到边缘节点、播放器预连接 DNS/连接复用。
- **卡顿**：自适应码率（ABR）动态降码率保流畅、合理的缓冲策略、必要时丢帧保时延。
- **成本**：CDN 回源量与带宽是直播的主要成本项，热房间的边缘命中率直接决定账单，见 [Cache](/docs/CS/SE/Cache.md)。
