## Introduction

`registry/` 是 Higress 里少数**真正自己写**的基础设施层——数据面借 Envoy、控制面借 pilot fork，而"从各种注册中心把服务搬进 xDS"这件事没有现成件可用。这一页记它的模型与实现事实（基准 v2.2.5，行号可复核）。

一句话模型：**每种来源一个 watcher，watcher 自己构造 `ServiceEntry`，塞进一个共享的 memory cache，最后由 `convertServiceEntry` 挂到 Istio 配置集合上**。链路层面它挂在 McpBridge 那条支路上，见 [Config Pipeline](/docs/CS/Framework/Higress/Config_Pipeline.md)。

## The Watcher Contract

`registry/watcher.go:54-62` 定义七个方法：`Run()`、`Stop()`、`IsHealthy() bool`、`IsReady() bool`、`GetRegistryType() string`、`AppendServiceUpdateHandler(f func())`、`ReadyHandler(f func(bool))`。`BaseWatcher`（`:64-84`）给默认实现，各具体 watcher 内嵌它——**注意 `BaseWatcher` 的 `Run` / `Stop` 是空实现、`IsHealthy` 恒返回 true**，也就是说"健康"这个概念在基类里是空的，具体 watcher 不覆写就永远显示健康。回调类型在 `:86-89`。

八个来源类型是 `registry/watcher.go:27-40` 的常量：`zookeeper`、`eureka`、`consul`、`nacos`、`nacos2`、`nacos3`、`static`、`dns`，另有 `Healthy` / `UnHealthy` 状态常量与 `DefaultDialTimeout = 3s`。文档说的"8 种 type"与代码逐字对应，**`registry/reconcile/reconcile.go:195` 的 `switch registry.Type` 八种全部分派到实现、default 分支报 "unsupported registry type"**，没有一个空缺：

| CRD type | 实现包 | 构造调用点 | FQDN 后缀 | Resolution |
| --- | --- | --- | --- | --- |
| `zookeeper` | `registry/zookeeper` | `reconcile.go:235` | `.zookeeper`（硬编码） | STATIC |
| `consul` | `registry/consul` | `:244` | `.<datacenter>.consul` | 阻塞查询（见下） |
| `eureka` | `registry/eureka` | `:267` | `.eureka` | STATIC |
| `nacos` | `registry/nacos`（SDK v1） | `:197` | `.分组.命名空间.nacos` | STATIC |
| `nacos2` | `registry/nacos/v2`（SDK v2） | `:212` | 同上，末段**写死** `nacos` | STATIC / DNS |
| `nacos3` | `registry/nacos/v2` + `nacos/mcpserver` | `:212` + `v2/watcher.go:109` | 同上 | 由 MCP 路线决定 |
| `static` | `registry/direct` | `:256` | `.<name>.static` | STATIC |
| `dns` | `registry/direct` | `:256` | `.<name>.dns` | DNS |

调和器 `Reconciler` 内嵌 `memory.Cache`（`reconcile.go:48-57`），watcher 的键是 `path.Join(registry.Type, registry.Name)`（`:111`），用 `reflect.DeepEqual` 把变更分成 toBeCreated / toBeUpdated / toBeDeleted（`:114-132`）——**"更新"的语义是 Stop 旧 watcher 再整体重建**（`:141-155`），不是热改配置。所有新 watcher 建好后要等 Ready，超时上限 `DefaultReadyTimeout = 60s`（`:45`、`:171-181`），到点报错。状态可经 `GetRegistryWatcherStatusList`（`:394-414`）从 `/registry/watcherStatus` 端点读出（注册点 `pkg/bootstrap/server.go:483`）。

`McpBridge.spec.proxies` 不走 watcher 工厂，由 `reconcileProxies`（`:334-381`）经 `proxy.BuildProxyWrapper`（`:366`）写进 cache 的 `ProxyWrapper` 槽，监听端口在 `:77-88` 自动回填；`registry/proxy/factory.go:200-222` 是 EnvoyFilter patch 模板（占位符 `{{name}}/{{type}}/{{address}}/{{port}}/{{proxy_name}}/{{cluster_name}}`）。**`registry/proxy/` 与 MCP 无关**，尽管它和 MCP server 都出现在 McpBridge 里。

## Memory Model

一个反直觉的点：**`registry/memory/` 没有自己的"服务实例"模型**。整个包只有一个 `cache.go`（454 行），核心存储是 `store.sew map[string]*ingress.ServiceWrapper`（`:76`），即复用 `pkg/ingress/kube/common/controller.go:222-231` 的 `ServiceWrapper`，字段为 `ServiceName`、`ServiceEntry`、`DestinationRuleWrapper`、`Suffix`、`RegistryType`、`RegistryName`、`ProxyConfig`、`createTime`。**实例级信息就是 `ServiceEntry.Endpoints []*v1alpha3.WorkloadEntry`**，由各 watcher 直接构造。另两个槽是 `configs map[string]map[string]*config.Config`（按 Istio GVK 分桶，`:74`）与 `pw map[string]*ingress.ProxyWrapper`（`:82`），内部键用 `ServiceName + "#@" + Suffix`（分隔符常量 `pkg/common/symbol.go:21`）。

`Namespace` 是固定字符串 `"mcp"`：`convertServiceEntry`（`pkg/ingress/config/ingress_config.go:931-973`）遍历 `GetAllServiceWrapper()` 后，把每个 ServiceEntry 包成 `config.Config{GVK: ServiceEntry, Name: Hosts[0], Namespace: "mcp", CreationTimestamp: ..., Labels: {higress-registry-type, higress-registry-name}}`（`:944-953`）。⇒ 在 `config_dump` 里看到 `mcp` 这个不存在于集群中的命名空间，是这套设计的正常产物；两个 label 常量定义在 `pkg/config/constants/constants.go:27-29`，它们是"这条服务来自哪个注册中心"的唯一可追溯标记。

`GetAllConfigs` 还有一处合成逻辑值得单独记：对 `gvk.WasmPlugin`，它会把所有 MCP 规则打包成**一个自动生成的插件**——`Name: "istio-autogenerated-mcp-wasmplugin"`、`Priority: 999`、`FailStrategy: FAIL_OPEN`（`registry/memory/cache.go:93-131`）。priority 999 意味着它排在极前，而 FAIL_OPEN 意味着 MCP 路由组件出问题时的取向是放行而不是拒绝。

## Naming Rules

通用形态是 `服务名.分组.命名空间.provider`，但各来源的真实拼装差别很大（逐处行号）：

| 来源 | host 构造 | 位置 |
| --- | --- | --- |
| nacos v1 | `host = serviceName + "." + join(groupName, namespaceId, w.Type)` | `registry/nacos/watcher.go:336-338` |
| nacos v2 / v3 | 同结构，但**末段写死字符串 `"nacos"`**，不取 `w.Type` | `registry/nacos/v2/watcher.go:555-557`、`:665` |
| consul | `服务名.datacenter.consul`（**没有分组与命名空间两段**） | `registry/consul/watcher.go:239`、`:287` |
| zookeeper | host 本身就是接口名（Dubbo）或 `app.路径段`（Spring Cloud，斜杠转连字符），`.zookeeper` 只作为 wrapper 的 `Suffix` 字段 | `registry/zookeeper/watcher.go:183-193`、`:335-337` |
| eureka | `app.eureka` | `registry/eureka/watcher.go:250` |
| static / dns | `w.Name + "." + w.Type` | `registry/direct/watcher.go:106` |
| nacos MCP 路线 | SE 后缀 `分组.命名空间.nacos`，**此处没有下划线替换步骤** | `registry/nacos/mcpserver/watcher.go:820-821` |

**下划线转连字符**的实现是 `strings.ReplaceAll(suffix, common.Underscore, common.Hyphen)`，落在 nacos v1 的 `watcher.go:337`（订阅回调）与 `:435`（`transformServiceEntry`，拆 dataId 的分组段）、v2 的 `:556` / `:666`，consul 侧则直接对整条 `service.datacenter.consul` 做替换（`:240` / `:288`）。代码未写注释，动机是 DNS 主机名惯例不允许下划线，`DEFAULT_GROUP` 因此变成 `DEFAULT-GROUP`。

`RegistryConfig.Name` 的作用被高估了：**nacos / zk / consul / eureka 的 host 都不含 registry name**，name 只进 `ServiceWrapper.RegistryName`、进而变成 label 与 watcher 键。**唯一例外是 static 与 dns**——host 直接用 `name.type`，所以**改一个 static/dns 来源的 `name`，会直接改变所有指向它的路由目标 FQDN**，进而打断所有写了这个名字的 Ingress。

## Timers and Units

三个 nacos watcher 各自定义了同值常量：`DefaultRefreshInterval = 30s` 与 `DefaultRefreshIntervalLimit = 10s`（`registry/nacos/watcher.go:48-49`、`v2/watcher.go:57-58`、`mcpserver/watcher.go:55-56`）。CRD 字段 `NacosRefreshInterval int64`（`api/networking/v1/mcp_bridge.pb.go:132`）被当作 `time.Duration(int64)` 直接使用（`nacos/watcher.go:209`、`v2/watcher.go:336`）——**`time.Duration` 的单位是纳秒，所以"这个字段按纳秒填"与代码一致**，小于下限会被钳到 10s（`:156-157`、`:253-254`、`:211-212`）。同一个 watcher 家族里 `NacosTimeout` 却是**毫秒**（`DefaultNacosTimeout = 30000`，`v2/watcher.go:49`，传给 `constant.WithTimeoutMs`，`:151-152`）——两个字段单位不同，是本层最容易写错的一处。

consul 同样 30s / 10s（`consul/watcher.go:37-38`）并有一个 `ConsulHealthPassing = "passing"`（`:36`）；eureka 只有 `DefaultFullRefreshIntervalLimit = 30s`（`eureka/watcher.go:37`）——**`WithEurekaFullRefreshInterval` 选项存在但全仓没有任何调用点**（reconcile 的 eureka 分支只传 5 个基础参数，`reconcile.go:266-274`），所以 eureka 的刷新周期在 CRD 层不可配。

地址服务器发现是 nacos v2 独享：`registry/nacos/address/address_discovery.go:31-36` 定义 `NACOS_PATH = "/nacos/serverlist"`、请求头 `Request-Module: Naming`、`DEFAULT_INTERVAL = 30s`，`Run()`（`:64-77`）每 30s 拉一次 server 列表。reconcile 只在 nacos2/nacos3 分支传 `WithNacosAddressServer`（`reconcile.go:216`），v1 分支没有这个选项。

## Per-Registry Behavior

**Nacos 三代。** `go.mod:33-34` 同时挂着 `nacos-sdk-go v1.0.8` 与 `.../v2 v2.3.5`：v1 watcher 用 `clients.NewNamingClient`（`nacos/watcher.go:112-113`）+ ticker 全量 `GetAllServicesInfo`（`:209`、`:239`）+ 逐服务 `Subscribe`（`:306`）；v2 watcher 结构同构（`:335-336`、`:525-528`，回调工厂 `getSubscribeCallback:554`）。**`nacos3` 不是独立 watcher**，而是 v2 watcher 在特定条件下额外派生一个 mcpserver watcher（`v2/watcher.go:109-141`，存进 `w.mcpWatcher`），默认 `RegistryType: provider.Nacos2`（`:90`）。至于"v1 走 HTTP 长轮询、v2 走 gRPC 长连接"，本仓只能看到 SDK 代际与用法差异，**传输层实现未在一手代码里**（属 SDK 内部，见 Unverified）。

**ZooKeeper。** 常量在 `registry/zookeeper/types.go:24-26`：`DUBBO = "/dubbo/"`、`SPRING_CLOUD_SERVICES = "/services"`、`DUBBO_SERVICES = "/dubbo"`。默认 `zkServicesPath: []string{"/services"}`（`watcher.go:84`），而 `fetchAllServices` **先无条件扫 `/dubbo`（`:209`）再按配置扫 Spring Cloud 根路径（`:213-214`）**——所以 `zkServicesPath` 只能改 Spring Cloud 那半边，Dubbo 是硬编码必扫。Dubbo 子节点名即接口名（`:183`），provider 路径 `/dubbo/<接口>/providers`（`:241`），URL 做 `%3D→=`、`%26→&` 反转义后剥前缀（`:419-420`、`:433`）。产物 `Resolution: STATIC` + WorkloadEntry 端点（`:650-663`）；客户端库是 `dubbogo/go-zookeeper/zk`（`:28-29`）。

**Consul。** 机制是 hashicorp 的 `watch.Plan` 阻塞查询（`watchers map[string]*watch.Plan`，`consul/watcher.go:48`；`plan.Token` `:279`）。`ConsulServiceTag` 读入即 `ToLower + TrimSpace`（`:99`），`ConsulDatacenter` 走选项（`:85-89`）。

**Eureka。** 是**完整实现**而非占位：306 行 watcher 加 `client/` 三个文件（`http_client.go` / `plan.go` / `struct.go`），base URL 由 `net.JoinHostPort(Domain, Port)` 拼（`:78`），产物 STATIC + WorkloadEntry（`:297-302`）。

**static 与 dns 是同一个 watcher**（`registry/direct/watcher.go`，270 行），按 `w.Type` 分叉：static 解析 `ip:port` 与 `[IPv6]:port`（`:147-186`）→ STATIC（`:218`）；dns 先用 `domainRegex` 校验（`:140`）→ DNS（`:219-220`）。它还顺手做了两件事：**协议为 HTTPS 时自动生成 TLS SIMPLE 的 DestinationRule**（`:225-246`），**DNS 类型只有一个端点时 SNI 自动取域名**（`:262-263`）。

## Credentials

`registry/auth_option.go:17-23` 的 key 常量全集是五个：`nacosUsername`、`nacosPassword`、`etcdUsername`、`etcdPassword`、`consulToken`（文档提到的三个逐字一致；etcd 两个没有任何消费者，`registry/` 下也不存在 etcd watcher 目录，属死代码）。

取用逻辑在 `reconcile.go:298-332`：读 `registry.AuthSecretName`，为空则返回零值；否则 `Secrets(r.namespace).Get(...)`——**Secret 必须与控制器同命名空间，取不到就让整个 watcher 创建失败**（`:307-309` 返回 error，向上传播）。所以"配了 authSecretName 但 Secret 名字写错"的表现是来源完全不生效，而不是降级为匿名。

真正消费 authOption 的只有三处：consul 的 token（`consul/watcher.go:135`、`:157`、`:279`）、nacos v2 的用户名密码（`v2/watcher.go:164-165`，AK/SK 另走 CRD 明文字段 `:162-163`）、mcpserver watcher（`mcpserver/watcher.go:141-142`）。**`nacos`（v1）拿到 authOption 却从未使用**：字段在 `nacos/watcher.go:68`、选项在 `:202-204`、reconcile 也确实传了（`reconcile.go:208`），但它的 `constant.NewClientConfig(...)`（`:96-105`）里没有任何凭据项，全文件再无第二处引用。⇒ 认证在 v2.2.5 的精确适用范围是 **nacos2 / nacos3 / nacos3-mcpserver / consul**；`eureka`、`zookeeper`、`direct`（static / dns）没有认证通路，zk 的 `NewWatcher` 参数里根本没有凭据位（`reconcile.go:235-242`）。

## MCP Server Route

三个字段定义在 `api/networking/v1/mcp_bridge.pb.go:141-143`：`McpServerExportDomains`（field 20）、`McpServerBaseUrl`（21）、`EnableMCPServer`（22，`*wrappers.BoolValue`）。传递链只有一条：reconcile 的 nacos2/nacos3 分支 → `WithMcpExportDomains` / `WithMcpBaseUrl` / `WithEnableMcpServer`（`reconcile.go:226-228`）→ v2 watcher 选项（`:307/:313/:319`）→ 条件成立时转交给 mcpserver watcher（`v2/watcher.go:123-125`）。

**"仅 nacos3"这条限制在代码里是软校验**：`v2/watcher.go:105-108` 的分支是"开了 `EnableMCPServer` 但 type 不是 `nacos3` ⇒ 打一条 `log.Errorf("can not create mcpWatcher for nacos 2.x type, required nacos 3.x")` 然后继续"。也就是说 **nacos2 上配了 MCP 开关不会报错、不会影响普通服务发现，只是静默不开 MCP**，且 `registry/` 层没有任何 admission 校验；console 是否在 API 层补了这道校验未核实（独立仓库）。

mcpserver watcher 的产出是**一组自动生成的资源**，命名规则在 `registry/mcp_model.go:20-25` 的常量与 `mcpserver/watcher.go:400/421/440/545/623` 的格式化：`istio-autogenerated-mcp-{vs,se,dr,httproute,mcpserver}-<dataId 去掉 .json>`。`McpServerExportDomains` 用作 VirtualService 的 hosts（`:532`、`:619`），`McpServerBaseUrl` 作为路径前缀合并（`:548-549`）。数据模型侧：`McpServerRule` 带 `_rules_` / `_match_route_` 的 json tag（`registry/mcp_model.go:39`、`:43`——注意**这与 WasmPlugin 转换用的下划线键同名但无关**，前者是 MCP 配置模型，后者是 `ingress_config.go:1332/1276` 的字面量），`McpTool` 含 `RequestTemplate`（`:83-92`）与 `ResponseTemplate`（`:99-103`）与 `ToolSecurity.credential`（`:65-69`），协议枚举为 `stdio / http / https / dubbo / mcp-sse / mcp-streamable`（`:27-32`），模板类型 `json-go-template`（`:18`）。闭环是：watcher 写 `Cache.UpdateConfigCache` → `GetAllConfigs(gvk.WasmPlugin)` 现场打包成那个 priority 999 的自动插件 → `Reconciler.GetMcpServers()`（`reconcile.go:383-392`）供配置层读取。

## Call Chain

1. McpBridge 事件 → `AddOrUpdateMcpBridge`（`ingress_config.go:1417-1428`，先过 `name == "default"` 门）→ 懒构造 `reconcile.NewReconciler(...)`（`:1429` 起，闭包负责向 XDS 侧广播五类合成资源）。
2. `Reconcile(mcpbridge)`（`reconcile.go:72`）→ 回填 proxy 监听端口（`:77-88`）→ `reconcileRegistries(spec.registries)`（`:94`）→ `reconcileProxies(spec.proxies)`（`:97`）→ `PurgeStaleItems()` 有清除则触发一次 `serviceUpdate()`（`:101-104`）。
3. `reconcileRegistries` 做三分类 diff（`:108-135`）→ 对每个新配置走 `generateWatcherFromRegistryConfig`（`:186`）：先 `getAuthOption`（`:190` → `:298` 读 Secret）→ `switch` 建 watcher（`:195`）→ `go watcher.Run()`（`:152` / `:164`）→ 等 Ready（`:171-181`，60s）。
4. `watcher.Run()`（以 nacos v2 为例，`:335-`）ticker 全量 + `Subscribe` 增量 → 组 `ServiceEntry` / `WorkloadEntry`（`:624-642`）→ `cache.UpdateServiceWrapper(host, ...)` → `w.UpdateService()`。
5. `serviceUpdate` 回到配置层：`convertServiceEntry`（`ingress_config.go:931`）从 `GetAllServiceWrapper()` 产出 Istio config（Namespace `"mcp"`），与 `GetAllConfigs` 的 MCP 自动资源合并去重（`:960-971`）后交给 pilot。

## Unverified

nacos SDK 的传输层差别（v1 长轮询 / v2 gRPC）未读 SDK 源码；v1 的 `DefaultNacosTimeout` 数值未读到（v2 是 30000）；consul 的 `ConsulServiceTag` 过滤落点与 SE Resolution 取值未逐行核对（`consul/watcher.go:160-235` 未读）；eureka 的 `deltaRefreshIntervalLimit` 默认值与 delta 轮询实现（`client/plan.go`）未读；zk Dubbo provider URL 的权重 / 分组解析细节（`watcher.go:380-450` 只扫到反转义与剥前缀）；`--keepStaleWhenEmpty` 的默认值与消费点；`higressconfig.McpServerWasmImageUrl` 常量实际值；`mcpserver/client.go` 的凭据模板解析细节（`CredentialPrefix:324`、`${nacos.` 模板 `:351` 只到行号）；console 是否对 `enableMCPServer` + type 组合做前置校验；v2 watcher 里 `ServiceEntry_DNS` 的完整判定条件。
