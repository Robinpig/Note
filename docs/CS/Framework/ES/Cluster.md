

Elasticsearch (ES) 集群的实现是一个经典的分布式系统设计案例。它通过分片（Sharding）、复制（Replication）、分布式协调和近实时（NRT）存储等机制，实现了海量数据的水平扩展、高可用和高性能搜索。


ES 集群由多个节点（Node）组成，它们通过内部网络通信协同工作。

基本数据单元：
索引（Index）：逻辑上的数据集合，类似于关系型数据库中的“Database”。
分片（Shard）：由于单个节点硬件资源有限，ES 将索引切分为多个更小的工作单元，即“分片”。分片是 ES 水平扩展的核心。
副本（Replica）：主分片的拷贝。用于提供高可用（节点宕机时不丢数据）和读负载均衡（搜索请求可以分发到副本上）。

节点角色（Node Roles）：
Master Node（主节点）：负责轻量级的集群管理操作，如创建/删除索引、跟踪哪些节点属于集群、决定分片在节点间的分配（Allocation）。
Data Node（数据节点）：实际存储数据分片并执行 CRUD、搜索和聚合等消耗 CPU/内存/IO 操作的节点。
Coordinating Node（协调节点）：接收客户端请求，将请求转发给相关节点，汇总结果并返回。集群中的所有节点默认都是协调节点。
Ingest Node（预处理节点）：在索引文档之前执行数据预处理（Pipeline）。



分布式系统必须解决“节点如何互相发现”以及“谁来当老大（主节点）”的问题。
1. 节点发现 (Discovery)
节点启动时，会通过配置的 seed_hosts（种子节点列表）发送 Ping 请求，发现网络中的其他节点，并交换集群状态（Cluster State）。
集群状态包含了集群中有哪些节点、有哪些索引、分片分布在哪些节点上等元数据。
2. 主节点选举与防“脑裂” (Split-Brain)
当集群启动或原主节点宕机时，需要选举出新的 Master。如果发生网络分区，集群可能会被割裂成两个小集群，各自选出 Master 并接收写请求，导致数据无法合并，这就是脑裂。

ES 7.x 引入了基于类似 Raft 协议的自动引导机制（Cluster Bootstrap）。只要初始配置好候选主节点列表，系统会自动计算法定人数，彻底废弃了手动配置法定人数的参数，极大地降低了脑裂风险和运维复杂度。




数据写入流程（Write Path）
当客户端向集群发送一条写文档（Document）请求时，流程如下：
路由计算（Routing）：
请求首先到达任意一个协调节点。协调节点根据文档的 _id（或自定义的 routing 字段）计算 Hash 值，决定文档该去哪个分片。
公式：shard = hash(routing) % number_of_primary_shards
(这也是为什么 ES 的主分片数量一旦创建就无法直接修改的原因，修改会导致路由错乱。)
转发到主分片：协调节点将请求转发到目标主分片（Primary Shard） 所在的节点。
主分片执行写入：主分片节点将数据写入内存 Buffer，并同时写入 Translog（事务日志，防止断电丢失数据）。
并发同步副本：主分片将写操作并发转发给该分片的所有副本分片（Replica Shards）。
响应客户端：当主分片和所有副本分片都报告成功后（或达到了配置的 wait_for_active_shards 阈值），主分片向协调节点确认，协调节点再向客户端返回成功状态。





数据搜索流程（Search Path）
ES 的搜索采用了著名的 两阶段查询（Query Then Fetch） 机制：
阶段一：Query（查询阶段）
协调节点将搜索请求广播到该索引的所有分片（主分片或副本分片均可，以此实现读负载均衡）。
每个分片在本地执行搜索，对匹配到的文档进行局部排序，并返回给协调节点一个轻量级的结果集（仅包含文档 ID 和相关性得分 Score，不包含完整文档内容）。
协调节点汇总所有分片的结果，进行全局排序，计算出最终需要的 Top N 文档 ID（例如第 1 到 10 名）。
阶段二：Fetch（获取阶段）
协调节点根据上一步得出的文档 ID，直接去对应的数据节点上获取完整的文档数据（Fetch）。
数据节点将完整文档返回给协调节点。
协调节点将最终的完整结果集返回给客户端
