## Introduction

etcd 历史上有两套 API：**v2**（HTTP/JSON，老）和 **v3**（gRPC，现代）。v2 自 etcd 3.4 起被标记为 deprecated，3.5 正式废弃（`--enable-v2` 进入 deprecated 状态），到 **3.6 被彻底移除**——`--enable-v2` 与 `--experimental-enable-v2v3` 两个 flag 在 3.6 的 release notes 里明确列在「Flags removed」中。

> [!WARNING]
> 如果你还在用 v2 API，**3.5 是最后一个能启用 v2 的版本**。升级到 3.6 之前必须先把 v2 数据迁走或确认 v2store 已清空，否则 `etcdutl check v2store` 会拦住升级。3.6 即便删了 v2 API，启动仍会从 legacy v2 snapshot 引导（这是个已知不一致，社区计划改成从 v3store 引导，见 issues/12913）。

## v2 与 v3 的核心差异

理解为什么移除 v2，先看两套 API 的根本不同：

| 维度 | v2 | v3 |
| :--- | :--- | :--- |
| 协议 | HTTP/1.x + JSON | gRPC（[HTTP/JSON 网关](/docs/CS/Framework/etcd/gateway.md) 兼容） |
| 数据模型 | **目录树**（`/a/b/c` 层级，父子是数据结构的一部分） | **扁平 key + 前缀范围查询**（`/a/b` 只是 key 的一部分） |
| TTL | 在 **每个 key** 上（TTL 属性挂在 key） | 在 **Lease** 上（一个 lease 可挂多个 key，见 [lease](/docs/CS/Framework/etcd/lease.md)） |
| 监听 | **长轮询**（watch 持续逐条、历史不连续，断线需从头回放） | **历史事件流**（Watch 从指定 revision 连续回放，见 [watch](/docs/CS/Framework/etcd/watch.md)） |
| 一致性 | 最终一致（leader 转发、读可能落后） | 默认线性一致（[ReadIndex](/docs/CS/Framework/etcd/read.md)） |
| 多版本 | 无，覆盖即丢 | [MVCC](/docs/CS/Framework/etcd/MVCC.md)，每次写生成新 revision |
| 事务 | 无 | [Txn](/docs/CS/Framework/etcd/etcd.md)（CAS/put/get 组合） |
| 存储引擎 | 自研 v2store（内存树 + 快照） | [boltdb](/docs/CS/Framework/etcd/boltdb.md) + MVCC |

最关键的工程差异是 **TTL 模型**：v2 时代每个 key 自带 TTL，即使 TTL 相同、key 不同，客户端也得为每个 key 维持一条独立 HTTP/1.x 连接定时续期——不支持多路复用，规模一大就扛不住。v3 把 TTL 抽到 Lease 上，相同 TTL 的 key 复用同一 lease，再配合 gRPC HTTP/2 多路复用，续期连接数大幅下降。这正是 v3 Lease 设计的动机之一。

另一个差异是 **watch 的连续性**：v2 的 watch 是 HTTP 长轮询，断线后只能从当前时间往后、拿不到断线期间的事件；v3 的 watch 带 revision，断线重连能从断点 revision 连续回放（[watch.md](/docs/CS/Framework/etcd/watch.md) 的 progress notify / resume 机制），对「不能丢事件」的协调场景（如选主、配置推送）可靠得多。

## 为什么移除 v2

- **维护负担**：v2store 与 v3 的 boltdb+MVCC 是两套并存存储，任何改动都要顾两头。v2 的目录树淘汰过期 key 还是 O(N) 遍历（v3 用最小堆 O(log N)，见 [lease.md](/docs/CS/Framework/etcd/lease.md) 的 checkpoint/淘汰说明）。
- **功能割裂**：v2 没有 MVCC、没有 Txn、watch 不可靠，新特性只长在 v3 上，v2 成了纯包袱。
- **bootstrap 不一致**：3.6 仍从 legacy v2 snapshot 引导，但 v2 API 已删——社区计划改从 v3store 引导消除这层不一致。

## 迁移路径

升级到 3.6 前（官方 [upgrade_3_6](https://etcd.io/docs/v3.6/upgrades/upgrade_3_6/) 清单）：

1. **确认所有成员从未开过 v2**：如果任何成员的 `--enable-v2` / `ETCD_ENABLE_V2` 从来没启用过（始终 unset 或 false），直接可升 3.6。
2. **否则先检查 v2store**：用 `etcdutl check v2store`（**必须用 3.5.32+**，扩展了对 WAL 记录的扫描，不只看 v2 snapshot）。输出四种之一：
   - `No custom content found` → v2store 干净，跳到第 4 步；
   - 只在 v2 snapshot 有自定义数据 → 按 v2 migration guide 迁或删除；
   - 只在 WAL 有 → 等下一次 v2 snapshot 自动清（或强制 snapshot）；
   - 两处都有 → 按 migration guide 处理。
3. 解决后重跑 `check v2store` 直到干净。
4. 从所有成员移除 `--enable-v2` / `ETCD_ENABLE_V2`，再升 3.6。

v2 自定义数据若想保留到 v3，走官方 **v2 migration guide**（利用 3.5 的 `--experimental-enable-v2v3` 把 v2 请求桥接到 v3 store 做迁移）。注意 `--experimental-enable-v2v3` 同样在 3.6 被删。

## 3.6 相关的其它破坏性变更

和 v2 移除同期、升级时容易踩的：

- `--enable-v2` / `--experimental-enable-v2v3` / `--proxy` 系列（含 `--proxy-refresh-interval` 等）全部移除——后者意味着 3.6 的 `etcd` 二进制**不再内置 grpc-proxy**，需另跑 `etcd grpc-proxy`（见 [gateway.md](/docs/CS/Framework/etcd/gateway.md)）。
- **`--snapshot-count` 默认值从 100000 降到 10000**（3.6）——Raft 层更频繁打快照，换来相比 3.5 约 50% 的内存下降；若你的负载依赖大 snapshot 间隔，升级后需重新评估（详见 [tuning.md](/docs/CS/Framework/etcd/tuning.md)）。
- `--experimental-*` 大量转正为正式 flag（如 `--compaction-batch-limit`、`--corrupt-check-time`），旧的 experimental 名废弃。
- raft 从 etcd 仓库内迁出为独立 `raft` module（3.6 起 `go.etcd.io/raft` v3.6.0）；bbolt 升到 v1.4。
