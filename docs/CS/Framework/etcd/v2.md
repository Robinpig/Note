# V2 and V3

## Introduction

etcd 历史上有两套 API：**v2**（HTTP/JSON，老）和 **v3**（gRPC，现代）。v2 自 3.4 起 deprecated，3.5 里 `--enable-v2` 进入 deprecated 状态，3.6 移除相关 flag，而到 **3.7.4 启动已完全从 v3store 引导**——`bootstrap.go` 的 `buildConfStateFromV3store` 从 backend 成员表重建 `ConfState`，`EtcdServer.run()` 里已无 v2store 的 TTL 同步逻辑。

> 版本基线：etcd 3.7.4（commit 2e8a5c99，Go 1.26）。以下状态均以该 tag 源码为准。

从源码核实的反直觉点：

- **`--enable-v2` 在 3.7.4 的 config.go 里零命中**，flag 已彻底移除，不是"默认关闭"。
- **启动从 v3store 引导**，不是旧资料说的"3.6 仍从 legacy v2 snapshot 引导、计划改成 v3store"——3.7.4 已完成切换。
- **`V2Deprecation` 枚举仍在**，用于 3.5 ↔ 3.6 平滑升级/回滚；`V2Depr2Gone`（v2store 既不写也不读）注释写明将在 3.8 清理。

## Core Differences

理解为什么移除 v2，先看两套 API 的根本不同：

| 维度 | v2 | v3 |
| :--- | :--- | :--- |
| 协议 | HTTP/1.x + JSON | gRPC（[HTTP/JSON 网关](/docs/CS/Framework/etcd/gateway.md) 兼容） |
| 数据模型 | **目录树**（`/a/b/c` 层级是数据结构的一部分） | **扁平 key + 前缀范围查询**（`/a/b` 只是 key 的一部分） |
| TTL | 在**每个 key** 上 | 在 **Lease** 上（一个 lease 挂多个 key，见 [lease](/docs/CS/Framework/etcd/lease.md)） |
| 监听 | **长轮询**（逐条、历史不连续，断线需从头回放） | **历史事件流**（从指定 revision 连续回放，见 [watch](/docs/CS/Framework/etcd/watch.md)） |
| 一致性 | 最终一致（leader 转发、读可能落后） | 默认线性一致（[ReadIndex](/docs/CS/Framework/etcd/read.md)） |
| 多版本 | 无，覆盖即丢 | [MVCC](/docs/CS/Framework/etcd/MVCC.md)，每次写生成新 revision |
| 事务 | 无 | [Txn](/docs/CS/Framework/etcd/features.md)（CAS/put/get 组合） |
| 存储引擎 | 自研 v2store（内存树 + 快照） | [boltdb](/docs/CS/Framework/etcd/boltdb.md) + MVCC |

最关键的工程差异是 **TTL 模型**：v2 每个 key 自带 TTL，即使 TTL 相同、key 不同，也得为每个 key 维持一条独立 HTTP/1.x 连接定时续期，不支持多路复用。v3 把 TTL 抽到 Lease 上，相同 TTL 的 key 复用同一 lease，配合 gRPC HTTP/2 多路复用，续期连接数大幅下降。这正是 v3 Lease 设计的动机之一。

另一个差异是 **watch 连续性**：v2 watch 断线后只能从当前时间往后、拿不到断线期间事件；v3 watch 带 revision，断线重连能从断点连续回放（[watch.md](/docs/CS/Framework/etcd/watch.md) 的 progress notify / resume 机制），对"不能丢事件"的协调场景（选主、配置推送）可靠得多。

## Why V2 Was Removed

- **维护负担**：v2store 与 v3 的 boltdb+MVCC 是两套并存存储，任何改动都要顾两头。v2 淘汰过期 key 是 O(N) 遍历（v3 用最小堆 O(log N)）。
- **功能割裂**：v2 没有 MVCC、没有 Txn、watch 不可靠，新特性只长在 v3 上。
- **bootstrap 不一致**：3.7 起统一从 v3store 引导（`buildConfStateFromV3store`），消除了 v2 snapshot 引导的历史包袱。

## V2Deprecation Enum

3.7 仍保留 `V2Deprecation` 配置，用来控制 v2store 的处置级别、支持 3.5 ↔ 3.6 平滑升级。定义在 `server/config/v2_deprecation.go`：

```go
type V2DeprecationEnum string

const (
	// V2Depr0NotYet means v2store isn't deprecated yet.
	// Default in v3.5, and no longer supported in v3.6.
	V2Depr0NotYet = V2DeprecationEnum("not-yet")

	// V2Depr1WriteOnly means only writing v2store is allowed.
	// Default in v3.6. Meaningful v2 state is not allowed.
	V2Depr1WriteOnly = V2DeprecationEnum("write-only")

	// V2Depr1WriteOnlySkipCheck is like V2Depr1WriteOnly, but bypasses the v2 content check.
	// Use only for 3.5 -> 3.6 upgrades with existing v2 data.
	V2Depr1WriteOnlySkipCheck = V2DeprecationEnum("write-only-skip-check")

	// V2Depr1WriteOnlyDrop means v2store is WIPED if found !!!
	// Will be default in 3.7.
	V2Depr1WriteOnlyDrop = V2DeprecationEnum("write-only-drop-data")

	// V2Depr2Gone means v2store is completely gone. The v2store is
	// neither written nor read. Anything related to v2store will be
	// cleaned up in v3.8.
	V2Depr2Gone = V2DeprecationEnum("gone")

	// V2DeprDefault is the default deprecation level.
	V2DeprDefault = V2Depr1WriteOnly
)
```

`IsAtLeast` 用 `level()` 把枚举映射成 0/1/2/3 做比较，`serveClients` 里的 `--enable-v2` 与 deprecated 级别互斥检查就是基于它。注意源码注释：`write-only-drop-data` 标注"Will be default in 3.7"，而 `V2DeprDefault` 常量本身仍是 `write-only`——升级/回滚场景要按实际生效值判断，别只看常量名。

## Migration Path

升级到 3.6+ 前（官方 upgrade_3_6 清单）：

1. **确认所有成员从未开过 v2**：若 `--enable-v2` / `ETCD_ENABLE_V2` 从未启用过（始终 unset 或 false），直接可升。
2. **否则先检查 v2store**：用 `etcdutl check v2store`（**必须 3.5.32+**，扩展了对 WAL 记录的扫描）。输出四种之一：`No custom content found`（干净）、只在 v2 snapshot 有、只在 WAL 有、两处都有。
3. 按结果迁移或等待下次 v2 snapshot 自动清理，重跑 `check v2store` 直到干净。
4. 从所有成员移除 v2 相关配置，再升级。

v2 自定义数据要保留到 v3，走官方 v2 migration guide（利用 3.5 的 `--experimental-enable-v2v3` 桥接迁移；该 flag 在 3.6 同样被删）。

## Other Breaking Changes

和 v2 移除同期、升级时容易踩的（以 3.7.4 为准）：

- `--enable-v2` / `--experimental-enable-v2v3` / `--proxy` 系列全部移除；3.6 的 `etcd` 二进制不再内置 grpc-proxy，需另跑 `etcd grpc-proxy`（见 [gateway](/docs/CS/Framework/etcd/gateway.md)）。
- **`--snapshot-count` 默认值从 100000 降到 10000**（3.7.4 的 `etcdserver.DefaultSnapshotCount = 10000`）——Raft 层更频繁打快照，换来相比 3.5 约 50% 内存下降（详见 [tuning](/docs/CS/Framework/etcd/tuning.md)）。
- raft 外置为独立 module `go.etcd.io/raft/v3` **v3.7.0**（3.6 起 v3.6.0）；bbolt 升到 **v1.5.0**（见 [tracker](/docs/CS/Framework/etcd/tracker.md)）。
- `/livez` / `/readyz` 健康端点自 v3.5.12 起提供（见 [monitoring](/docs/CS/Framework/etcd/monitoring.md)）。
