## Introduction

数据治理解决的是一个规模带来的问题：表只有几十张时，"这张表是谁建的、数据准不准、能不能删、改了会影响谁"都能靠人记、靠问。表涨到几千上万张、每天几百个作业在上面跑之后，这些问题必须**有系统来回答**，否则会出现两个典型症状——没人敢删任何东西（怕影响未知的下游），以及同一个指标在不同报表里数字不同（口径各自定义）。

治理不是审批流程，也不是给数据加锁。它是四件具体的事：**元数据采集**（知道有什么）、**血缘**（知道怎么来的、影响谁）、**数据质量**（知道能不能信）、**访问控制**（谁能看什么）。

> [!NOTE]
> 版本口径（2026-10 核实）：OpenMetadata **2.0.6**（2026-10-21）、DataHub **1.8.0**（2026-10-12）、Apache Atlas **2.5.0**（2026-04）。Amundsen 已于 **2026-09** 归档，仓库只读，新部署不应再选它。

## Four Kinds of Metadata

元数据不是一张表，至少分四层，缺任何一层治理都是跛的：

| 类别 | 内容 | 回答的问题 |
| :--- | :--- | :--- |
| 技术元数据 | schema、分区、文件格式、位置、统计信息 | 这张表长什么样、多大 |
| 业务元数据 | 业务口径、glossary 术语、指标定义、归属域 | 这个字段在业务上是什么意思 |
| 操作元数据 | 运行历史、行数趋势、查询频次、失败率、成本 | 它在不在用、跑得好不好 |
| 社会元数据 | owner、评分、评论、认证状态、文档 | 谁负责、能不能信 |

**技术元数据最容易采集**（连上 catalog 就能拿到），**业务元数据最难也最有价值**——"gmv 到底含不含退款"这类口径只能由人来定义，而它恰恰是指标不一致的根源。所以判断一个治理项目是否走过场，标准很直接：glossary 与指标定义有没有人维护。

## Data Catalog

catalog 在大数据里承担两个不同但容易混淆的角色，务必分开：

1. **表注册与定位**（"这个表名对应哪些文件"）——这是 [Hive](/docs/CS/DB/Hive/Hive.md) Metastore 的传统职责，也是 Spark / Trino / Flink 找表的地方。在湖仓里它升级为跨引擎的命名空间与权限边界，Iceberg 的 REST Catalog 就是往这个方向走的独立服务（见 [Table Format](/docs/CS/BigData/Table_Format.md)）。
2. **数据目录 / 资产发现**（"我该用哪张表"）——这是 OpenMetadata、DataHub 这类产品的职责，是给人用的搜索与理解层。

两者会被混为一谈是因为 HMS 长期兼任了两者，而它其实做不好第二件事：没有血缘、没有质量、没有 glossary、也没有像样的搜索。

## Lineage

血缘回答"这张表的数据从哪来、改动会影响谁"。它是治理里唯一能直接避免事故的能力——改上游表结构之前查下游影响面，以及指标异常时逐层上溯定位源头。

血缘有粗细之分：

- **表级血缘**：表 A → 表 B。采集容易，能回答"影响面多大"，但不够精确。
- **列级血缘**：表 A 的 `user_id` → 表 B 的 `uid`。能支撑字段级影响分析与口径追溯，采集代价高得多。

采集方式三种，可靠性递增、成本也递增：

1. **手工登记**：快但必然腐化，人不会持续维护。
2. **解析 SQL / 作业配置**：从查询日志、ETL 脚本、dbt manifest 里解析出输入输出。覆盖面取决于能拿到多少 SQL，且复杂 SQL 的解析容易出错。
3. **引擎侧标准事件**：作业运行时由插件直接上报，如 **OpenLineage** 规范（Airflow、Spark、Flink、dbt 都有集成）。这是当下最可靠的路线，因为它拿到的是**实际执行**的输入输出，而不是对代码的静态猜测。

选择建议很明确：**优先用 OpenLineage 这类运行时采集做主干，用 SQL 解析补充历史作业**。纯手工血缘基本等同于没有血缘。

## Data Quality

质量是把"我觉得数据有问题"变成"系统判定数据有问题"，手段是在管道上挂断言：

- **表级**：行数波动阈值、非空率、主键唯一性、分区是否按时到达（新鲜度）。
- **列级**：null 比例、值域范围、枚举合法性、唯一性、与参照表的外键匹配。
- **时序**：环比同比是否在合理区间——这是最能抓出"悄悄变坏"的一类，因为它不需要预先知道正确值。

质量规则的关键设计是**失败怎么办**：只告警不阻断，下游仍然会读到坏数据；一律阻断，则会被噪声规则拖垮整条链路。常见做法是按严重程度分级——阻断性规则（主键重复、行数归零）直接失败作业并告警，提示性规则（波动超阈值）只告警。

更新的形态是**数据契约（data contract）**：把 schema 与质量规则写成上下游之间的显式约定，上游违反即在入口被拦住。OpenMetadata 已支持导入 ODCS（Open Data Contract Standard）规则并转成可执行的测试用例。这个方向的价值在于把质量责任**前移到生产端**，而不是消费端各自校验。

## Access Control

大数据侧的权限模型与数据库类似但要处理更多层次：

- **RBAC / ABAC**：按角色或属性授权，粒度到库、表、视图。
- **列级与行级**：列掩码（column masking，敏感列按角色脱敏）与行过滤（row filter，只能看到自己部门的行）。这是合规场景的硬需求。值得注意的是这类能力正在下沉到**表格式协议层**——Iceberg 1.12 已把列掩码与行过滤加入 REST 规范，意味着多引擎可以共享同一套过滤规则，而不必在每个引擎里各配一遍。
- **与引擎的关系**：权限可以在 catalog 层统一定义，但**必须由执行引擎强制执行**。配置了 catalog 策略而引擎不认，等于没配。

Hadoop 生态里的传统组合是 Apache Atlas（元数据与分类）+ Apache Ranger（权限策略），这个组合仍适合深度使用 CDH/CDP 的存量环境。

## Tooling Landscape

| 工具 | 定位 | 特点 | 状态 |
| :--- | :--- | :--- | :--- |
| OpenMetadata | 一体化目录 + 质量 + 血缘 + 治理 | 130+ 连接器，内置数据质量与剖析，架构简单（MySQL/PostgreSQL + Elasticsearch，不用图库） | 活跃，2.0.6 |
| DataHub | 目录平台，push-based 实时血缘 | 事件驱动（Kafka 为核心），血缘新鲜度高，模块化，运维复杂度偏高 | 活跃，1.8.0 |
| Apache Atlas | Hadoop 生态的元数据与治理框架 | 与 Ranger 深度集成，标签驱动安全；功能面较窄 | 维护中，2.5.0 |
| OpenLineage | 血缘采集标准（非目录产品） | 规范 + 各引擎插件，与目录产品互补 | 活跃 |
| Marquez | OpenLineage 的参考实现 | 只做血缘后端，通常作为组件而非完整目录 | 发版缓慢 |
| Amundsen | 轻量数据发现 | 已归档 | **不应新用** |

选型判断：一体化开箱选 OpenMetadata；血缘实时性与大规模资产（千万级）是硬需求选 DataHub；已经在 CDH/CDP 上且强依赖 Ranger 选 Atlas；不论选哪个，**血缘采集都应走 OpenLineage 标准**，避免被单个目录产品绑死。

## Where to Start

治理很容易做成"买了工具但没人用"的项目。按收益排序的落地顺序是：

1. **先定 owner**：每张表必须有归属人。没有 owner 的元数据，其他一切都是空转——告警发给谁、删除要不要批，都无从谈起。
2. **接血缘**：影响面分析是唯一能让团队立刻感受到价值的能力。
3. **加质量断言**：从最要命的那几张核心表开始，只上少量高信噪比的规则。
4. **最后做 glossary 与指标定义**：最难，但它是"同一个指标不同数字"这个顽疾的唯一解。
