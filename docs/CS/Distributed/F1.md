# F1

## Introduction

F1 是 Google 在 2013 年（VLDB）公开的**分布式 SQL 数据库**，作为 [Spanner](/docs/CS/Distributed/Spanner.md) 的**查询层**存在：Spanner 提供全球分布、基于 TrueTime 的强一致 KV 存储与事务，F1 在其之上构建关系型 Schema、SQL 查询引擎与跨行事务。它的诞生背景是 Google 的 AdWords 系统——原本跑在分库分表的 MySQL 上，扩容与 schema 变更痛苦，需要既保留 SQL / 事务语义、又具备 Spanner 级别的可扩展性与可用性。

## Design Motivation

- **不复用 Spanner 的存储层**：F1 刻意解耦——存储与事务交给 Spanner，F1 专注查询。这样 Spanner 的演进不破坏 SQL 语义，F1 也能随查询需求独立迭代。
- **无阻塞 schema 变更**：大型表 Online DDL 不能锁表；F1 用 protobuf 列（行内以 protocol buffer 组织）支持无损 schema 演进。
- **跨地域**：复用 Spanner 的 TrueTime，使 F1 能跨数据中心部署而不牺牲外部一致性。

## Architecture

F1 分两层：

- **F1 Servers（无状态查询层）**：接收 SQL、生成分布式查询计划、向 Spanner 发 KV 读写。多副本、可水平扩展，故障时有其他 server 接管。
- **Spanner（有状态存储 / 事务层）**：提供 KV API、TrueTime 与分布式事务。

查询执行是**分布式**的：F1 server 把查询拆成算子树，下推部分计算（过滤、部分聚合）到 Spanner 层，减少广域网数据传输；大表扫描借助 Spanner 的 tablet 局部性。

## Key Mechanisms

- **层级 Schema + Protocol Buffer 列**：表行以 protobuf 存储，新增字段不会让旧行失效，schema 变更无需重写数据。
- **分布式查询优化**：统计信息跨 region 收集，优化器需把跨数据中心延迟（广域网 RTT）作为首要成本。
- **事务**：依赖 Spanner 的事务；F1 在 server 层实现应用级事务语义，避免长事务跨大量 F1 server。
- **快照查询**：支持时间旅行（snapshot at timestamp），得益于 Spanner 的多版本存储。

## Relation to Other Topics

F1 是"在强一致分布式存储之上构建 SQL"的最早工业范本，与 [CockroachDB](/docs/CS/Distributed/CockroachDB.md)（自己实现存储 + SQL）路线不同——F1 选择**复用** Spanner，CockroachDB 选择**自包含**。两者都证明"分布式 SQL"可行，但解耦方式相反。其底层时间语义与 [Time（时钟与同步）](/docs/CS/Distributed/Time.md) 中的 TrueTime 直接挂钩。
